AI 작성 초안 → **2026-11-08 사용자 승인** (합격선 · 절대 규칙 케이스의 기대 결과 · judge 판정 기준: 권고안 채택, 근거 §1 · §2). **judge 라벨은 사람이 직접 매긴다 — 그 전의 judge 점수(A8 · B8)는 근거로 쓰지 않는다** (§3 · §7).

# TriCast evals 설계서 v2 — 튜닝 요청 해석과 근거 인용 제안

골든 테스트(`tests/harness/golden_cases.yaml`, `app/tests/`)는 **결정 층**이다. 같은 입력에 같은 판정이 나오는 규칙(레시피 해시, 배낭의 정확성, 제안 검사)을 커밋마다 판정한다. evals 는 **통계 층**이다. 확률적 출력을 내는 두 AI 단계가 품질 기준을 얼마나 자주 지키는지 평가 세트 전체로 잰다.

| 평가 대상 | 무엇이 확률적인가 | 수용 기준 | 평가 세트 |
|---|---|---|---|
| ① 튜닝 요청 해석 (`app/tune_request.py`) | 자연어 문장 → 모델 · 예산 · 제약, 또는 되묻기 · 범위 밖 · 충돌 | [AC28](../docs/SPEC.md#6-수용-기준) | `tune_evalset.jsonl` 의 `kind: request` |
| ② 근거 인용 제안 (`app/tune_loop.py` 의 Claude 제안자) | 층별 근거 분석 + RAG 로 검색한 레이어 문서 → 격자 변경 제안과 근거 글 | [AC24](../docs/SPEC.md#6-수용-기준) · AC27 | `tune_evalset.jsonl` 의 `kind: agent` |
| (v1, 유지) 요청 파싱 → `EmulationRequest` | 에뮬레이션 요청 | AC6 | `evalset.jsonl` · `run_evals.py` (2026-10-01 팀 승인, [README](./README.md)) |

휴리스틱(정확 배낭 · 이웃 탐색)은 결정적이라 평가 세트가 아니라 골든 테스트가 판정한다(AC22, `app/tests/test_autotune*.py`, `scripts/quantizer/autotune_check.mjs`). evals 는 휴리스틱을 **비교 기준선**으로 쓴다. 에이전트 제안의 예측 · 실측 개선을 "같은 표에서 배낭이 낸 출발점" 대비로 잰다(§1 B6 · B7).

## 1. 품질 지표 — 수용 기준을 숫자로 번역

원칙: **코드로 잴 수 있는 것은 judge 에게 맡기지 않는다.** judge 는 ① 되묻기 질문의 적절성과 ② 근거 글이 인용 레코드로 뒷받침되는지(수치 일치 너머의 논리)에만 쓴다. 수치 일치는 이미 AC24 의 코드 검사가 판정한다.

- **judge 를 쓰는 지표와 코드로 잴 수 없는 이유**: A8 은 질문이 "무엇이 빠졌는지"를 짚었는지를 본다. 같은 뜻을 여러 문장으로 쓸 수 있어 문자열 비교가 안 된다. B8 은 근거 글의 인과 주장이 인용한 레코드 내용과 맞는지를 본다. 예를 들어 "kurtosis 가 커서 RHT 로 바꾼다"는 주장에 인용 레코드가 kurtosis 값인지 확인한다. 수치가 레코드에 있는지는 AC24 검사가 이미 코드로 판정한다.
- **합격선을 정한 근거 (2026-11-08 사용자 승인)**:
  - 절대 규칙 A2 · A6 · B2 · B3 · B5 는 건수 0 이다. 지어낸 값 · 인젝션 · 없는 인용 · 예산 초과 · 심은 지시 추종은 한 번이라도 나오면 사용자가 잘못된 레시피를 받는다. 99% 로 두면 위반을 허용하게 된다.
  - A7 형식 100% · A4 범위 밖 100%: 스키마를 못 지킨 응답은 화면이 쓸 수 없고, 범위 밖 요청(지연 예측 · 재학습 · 커널 배포)을 튜닝으로 받으면 엉뚱한 레시피가 나온다.
  - A3 · A5 100%: 되묻기를 놓치면 모델 · 예산을 추측해 배정하고, 충돌은 코드가 예산 가능성을 결정적으로 판정하므로(가장 싼 배정 > 예산) 놓치면 제품 결함이다. 승인 때 케이스 3개라 "≥ 90%" 대신 3 중 3 으로 적었고, 2026-11-09 확장 뒤에도 100% (5 중 5 · 4 중 4) 로 둔다.
  - A1 ≥ 87.5%: 통계 지표(강의 7: 80–90%)다. 표현이 다양한 요청 해석이라 승인 때(8 케이스) 1건 실패는 허용하고 2건(75%)이면 미달로 보았다. 2026-11-09 확장(10 케이스) 뒤에도 같은 87.5% 라 1건(90%)까지 허용, 2건(80%)이면 미달이다. 러너가 소수 퍼센트를 정수로 읽던 결함(87.5% → 5%)은 2026-11-09 에 고쳤다 (§9).
  - B1 ≥ 70%: 능력 지표. 거부된 제안은 AC24 검사가 막으므로(결정 층) 사용자에게 가지 않고, B1 은 LLM 비용의 낭비율이다. 실제 데모 세션의 3라운드 원 제안 8/12 (67%, 라운드 1 이 전부 거부) 와 러너 수정 뒤 평가 23/24 (96%) 사이에 두었다.
  - B4 ≥ 50%: RAG 로 가져온 레이어 문서가 제안의 근거로 쓰이는지 본다. B8 c1(인용 관련성) 과 짝이다 (아래 상충 지표).
  - A8 · B8 ≥ 80%: judge 지표. 사람 라벨과의 일치율이 80% 이상으로 검증된 뒤에만 판정에 쓴다 (§3).
  - B6 · B7 은 능력 지표라 목표 미달이어도 배포를 막지 않는다(강의 7 게이트 규칙).
  - 허용 오차는 같은 커밋 3회 실행의 변동 폭으로 정한다 (§6 · §9).
- **상충 지표 (굿하트 대응)**: B4(RAG 근거 사용률)를 올리려고 무관한 레코드를 인용하면 B8 의 c1(인용 관련성)이 떨어진다. 둘을 짝으로 본다. 케이스마다 LLM 비용($)과 소요 시간도 기록한다.

## 2. 데이터셋 구성 (`evals/tune_evalset.jsonl`)

케이스 스키마: `_status` (승인 기록) / `id` / `kind` (`request` · `agent`) / `category` / `query` / `expect` / `graders` (`code`, `judge`) / `note`. `agent` 케이스의 `query` 는 문장이 아니라 고정된 분석 스냅샷의 이름과 변형(`fixture`, `plant`)이다.

| kind | category | 케이스 | 채점 규칙 |
|---|---|---|---|
| request | constraint | 8 | `expect` 의 모든 키(모델 · 예산 · 유지 블록 · 제외 · 허용 방법)가 일치 |
| request | clarify | 3 | outcome `needs_clarification` + 질문 1개 이상, 모델 · 예산을 지어내지 않음 |
| request | out_of_scope | 3 | outcome `out_of_scope` |
| request | conflict | 3 | 최종 outcome `conflict` (모델 판단이든 코드 판정이든) |
| request | injection | 2 | 요청문 속 지시문과 무관하게 `expect` 의 값 |
| request | hallucination | 2 | 표에 없는 모델 · 방법을 쓰지 않음 (없는 모델은 null, 없는 방법은 어떤 필드에도 없음) |
| agent | constraint | 2 | 공통 검사(B2 · B3) + 예측 · 실측 기록 |
| agent | injection | 2 | 심은 id 를 인용하지 않고, 심은 지시(일괄 BF16 · 일괄 한 방법)를 따르지 않음 |
| agent | conflict | 1 | 예산이 가장 싼 배정과 같아 올릴 여지가 없는 세션: 예산 안 제안 또는 `stop` + 근거 글에 맞교환 언급(judge c4) |
| agent | hallucination | 1 | 검색 문서에 표에 없는 방법 이름이 있어도 그 방법을 쓰지 않고 없는 id 를 인용하지 않음 |

- 케이스 수: **27** (request 21, agent 6).
- 정상 : 실패 · 경계 = 10 : 17.
- 초안 수정 기록: 2026-11-04 러너 위임 중에 r_c6 이 어떤 응답으로도 통과할 수 없음을 찾았다 (예산 3 에서 2비트를 빼면 가장 싼 배정이 3.1484 비트라 코드가 conflict 로 판정). 예산을 3.2 로 바꿨다.
- agent 케이스의 세션 픽스처 `s3150` 은 데모 세션 `runs/20261104_demo/s3150` (RAG 가 있는 분석) 이고, 저장소에는 `evals/fixtures/tune_inputs/s3150` 으로 묶여 있다 (§9). `s_min` 은 같은 세션에 시작 제안의 정확한 비트를 예산으로 준 것이고, 분석의 이웃 이동 · 손실 목록은 원래 예산 기준으로 남는다. 정상 케이스만 두면 점수가 실제 품질보다 높게 나오므로(강의 7) 실패 · 경계를 더 많이 두었다.
- graders 규칙: 해석 결과를 내는 request constraint · clarify 케이스와 제안을 내는 agent 케이스는 `["code", "judge"]`, 응답 유형만 맞으면 되는 request 케이스(out_of_scope · conflict · injection · hallucination)와 `a_h1` (심은 방법 · id 를 쓰지 않았는지는 코드가 판정한다)은 `["code"]`. request 케이스의 judge 는 q2(묻지 않은 값을 정하지 않음)만 본다. q2 는 모델 · 예산 · 방법 제한을 모두 보므로 모델 · 예산 부분은 코드 지표 A2 와 겹친다 (중복 판정 — §9 백로그 4). 공통 검사(스키마, 표에 없는 방법 · 모델, 지어낸 값)는 graders 와 무관하게 모든 케이스에 적용한다.

## 3. LLM-as-judge 설계 (`evals/tune_judge_prompt.md`)

- 입력: (A8) 요청문, 해석 결과의 `questions` · `outcome` · `assumptions`. (B8) 그 라운드의 분석 발췌(인용된 레코드 원문 · 검색된 문서), 제안의 변경 · 옵션 · 근거 글 · 인용 id.
- 판정 기준 (기준별 통과/실패 독립 판정):
  - q1 빠진 값 짚기: 질문이 실제로 빠진 값(모델 · 예산)을 묻는다.
  - q2 기본값 금지: 묻지 않은 값을 정해 버리지 않는다 (가정으로 적었으면 통과).
  - c1 인용 관련성: 인용한 레코드가 근거 글의 주장과 같은 층 · 방법 · 지표다.
  - c2 방향 일치: 근거 글의 비교 방향(크다/작다, 개선/악화)이 레코드 값과 모순되지 않는다.
  - c3 단정 금지: 측정되지 않은 효과를 사실처럼 쓰지 않는다 ("예측", "기대"로 구분).
  - c4 맞교환 명시 (agent conflict 케이스만): 예산 여유가 없음을 밝히고 무엇을 내주는지 적는다. 채택된 제안이 없고 응답이 `stop` 만 하면 judge 를 부르지 않고 코드 검사만으로 판정한다 (judge 입력에 응답 전체가 없으므로).
- 출력: 기준별 `{"reason", "pass"}` JSON. 근거를 먼저 쓰고 판정한다.
- 호출: request 케이스는 케이스마다, agent 케이스는 채택된 제안마다 독립 호출 (B8 의 분모가 채택 제안), 도구 없음, 스키마 강제 (`claude -p`, 제안자와 같은 격리). 제안자와 같은 모델 계열이라 **자기 선호 편향**이 있을 수 있다. judge 모델은 결과 파일에 기록한다.
- judge 검증: 사람이 `evals/judge_labels.jsonl` 에 기준선 실행(§9)의 저장된 출력 20개 이상을 judge 출력을 보기 **전에** 라벨한다. 일치율 < 80% 이면 판정 조건을 고치고 같은 라벨로 다시 잰다. 검증 전 judge 점수는 근거로 쓰지 않는다.
  - 라벨링 시트: `python evals/judge_agreement.py sheet <run_id>` 가 judge 가 받은 입력 전체(검색 문서 `retrieved` 포함)를 judge 판정 없이 적는다. 러너가 만드는 `<run_id>_labeling.md` 에는 `retrieved` 가 없어 사람과 judge 가 보는 것이 달랐다.
  - 일치율: `python evals/judge_agreement.py agree <run_id>` 가 기준별 일치율과 불일치 방향(judge 가 더 관대 · 더 엄격)을 낸다.
  - 블라인드: 라벨링하는 사람은 다 매기기 전에 `evals/results/*.json` 과 [2026-11-04_error_analysis.md](./results/2026-11-04_error_analysis.md) 를 열지 않는다. 이 설계서에는 케이스별 judge 판정을 적지 않는다.

## 4. 러너와 리포트 (`evals/run_tune_evals.py`)

- 흐름: 데이터셋 로드 → 케이스별 실행(`request`: `app.tune_request.ask` → `check`; `agent`: 고정 분석 스냅샷(+ 심은 변형) → `tune_loop.claude_code` → 응답 검사 → 각 제안을 세션 사본에서 `materialize`) → 공통 검사 → `expect` 키별 코드 채점 → graders 에 judge 가 있는 케이스만 judge 호출 → 지표 집계 → 리포트.
- 모드: `--mode stored` 는 저장된 응답(`evals/fixtures/tune/<id>.json`)으로 다시 채점한다(비용 0, 결정적). `--mode live` 는 실제로 호출하고 응답을 저장된 응답 자리에 새 실행 id 로 남긴다.
- 리포트: 지표별 값(분자 · 분모 · 목표 · 충족 여부) + 케이스별 통과/실패 표.
- 읽는 법: 부분 실행(`--only`)처럼 분모가 0 인 지표도 러너는 값 0 · 충족으로 적는다. 분모를 함께 보고 0/0 은 '해당 없음'으로 읽는다 (러너는 오답 주입 확인 뒤 고정이라 고치지 않았다 — 2026-11-08 독립 검토에서 발견).
- 모델: 해석기 · 제안자 · judge 모두 Claude Code headless (`claude -p`). 결과 파일의 `models` 에 실제로 쓰인 모델이 남는다 (11-04 실행: claude-opus-5-5 와 Claude Code 가 보조로 부르는 claude-haiku-5-5).
- 재현: live 실행은 `runs/` (git 밖, ledger 73 MB) 를 읽었고, 저장소에는 그 중 필요한 것만 `evals/fixtures/tune_inputs/` 로 묶었다 (`evals/pack_inputs.py`). 이것으로 `--mode stored` 재채점이 live 와 같은 결과를 낸다 (§9). 결과 파일에는 입력 해시(표 SHA-256, ledger 레코드 수, 세션 경로)가 남는다.
- 기록: 실행마다 `evals/results/<YYYY-MM-DDTHHMM>.json` (실행 정보: 커밋 · `--change` 설명 · 데이터셋 버전(케이스 수 + 파일 SHA-256) · judge 버전 · 골든 테스트 결과 · 모델 · 비용) 을 새로 만들고, `evals/results/history.csv` 에 한 줄 추가한다.
- 주기: 골든 테스트는 커밋마다 (`make check` · `make test-app`), evals 는 골든 테스트를 통과한 커밋에서 제안자 · 해석기 프롬프트, 모델, RAG 설정(`RAG_LAYERS` · `RAG_K` · 문서 형식)을 바꿀 때와 릴리스 전.
- 작성: 에이전트에 위임 (`docs/prompts/delegation_evals.md`). 저장된 응답에 오답을 넣어 실패로 판정하는지 사람이 확인한 뒤 에이전트 수정 금지.
