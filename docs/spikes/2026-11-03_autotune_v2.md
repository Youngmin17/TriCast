# 스파이크: 보정 방법 · 패치 바닥 · KV 항목을 넣은 층별 표 (Auto-tune v2)

> v1 ([2026-10-13_autotune_mckp.md](./2026-10-13_autotune_mckp.md)) 6절의 재도전 조건 1~4 를 구현해 **같은 C1~C4 로 다시 판정**한다.

## 1. 가장 위험한 가정

**"층 하나만 바꾼 모델의 KL 표에 보정 방법(GPTQ · AWQ · SmoothQuant)을 후보로 넣고 패치 바닥을 빼면, 같은 크기에서 보정 방법을 쓰는
사람 레시피(`qd_mixed`)만큼 좋은 배정을 찾고(C4), 균일 배정보다 나은 것(C3)은 다른 모델에서도 성립한다."**

- 맞으면: Auto-tune 이 사람의 층별 혼합 레시피를 대신한다 (P3 · P9).
- 틀리면: 둘 중 하나다.
  - C4 실패: 층 하나를 보정한 값의 합은 보정 방법의 이득을 예측하지 못한다. 층 사이 보정 상호작용(입력 분포 변화)이 크다는 뜻이다.
  - Llama C3 실패: v1 결과가 Qwen3-0.6B 한 모델에서만 성립한다.
- 근거: v1 C4 미달은 대부분 KV 2비트 손실이었다. 사후 진단에서 KV 를 빼면 차이는 0.13 (0.6%) 이었다.

## 4. 방법

1. 표 (turin 또는 geneva A100 1장):
   ```
   python -m app.autotune table --model Qwen/Qwen3-0.6B --revision c1899de289a04d12100db370d81485cdf75e47ca --device cuda \
     --split validation --windows 8 --seqlen 512 --seed 42 --calibrate \
     --methods bf16,gptq_int4,awq_nvfp4,smoothquant_nvfp4,nvfp4,nvint4,mxfp4,mxfp8,int8,bfp12 \
     --calib-dataset wikitext2 --calib-samples 128 --calib-seqlen 2048 --calib-seed 42 \
     --kv-presets kivi2,kivi4,kv_fp8 --out table.json
   ```
2. 풀이: `solve --budget-bits` 를 9/2 · 285/56 · 1831/320 (KV 없음) · 1831/320 `--kv kivi2` 로 4회. 비교용으로 `--no-subtract-floor` 도 같은 예산으로 낸다.
3. C2:
   - `predict` 로 12개 레시피의 예측을 낸다.
   - `measure --calibrate --split validation --seed 43` 으로 같은 12개를 잰다.
   - 판정은 커밋된 `scripts/quantizer/autotune_c2.py` 로 한다. v2 에서는 예측값으로 `kl_sum_minus_floor` + `predicted_kv_kl_sum` 을 쓴다. 이 둘을 읽도록 고친 판은 결과를 보기 전에 커밋한다.
   - 창 겹침을 확인한다: validation seed 42 · 43 창끼리 (`--overlap --split validation`). 보정 창은 train 이라 split 으로 분리된다.
4. C3 · C4 PPL: `tricast run`, WikiText-2 test 전체 (146 × 2048 창). W2 · v1 과 같은 GPU 종류 (A100) 에서 잰다.
5. C3′: Llama-3.2-1B 에서 1번을 같은 설정으로 돌린다 (revision 은 클러스터 캐시의 SHA, 실행 기록에 남김). 그다음:
   - `solve --budget-bits 9/2` 로 Auto-tune 레시피를 낸다.
   - 그 레시피와 `qd_nvfp4` 격자의 PPL 을 같은 GPU 에서 잰다.
   - 격자 28행 가운데 16행 이후는 모델에 없는 블록이다 (`grid_blocks_beyond_model`).

### 4절 보충 — 반박 리뷰 뒤 · 측정 전에 바꾼 것 (2026-11-03, 이 파일의 첫 커밋 전)

반박 리뷰(Codex)가 "보정 창과 KL 창이 둘 다 WikiText-2 train 에서 뽑혀 겹칠 수 있다"고 지적했다.
확인해 보니 구조적 겹침이었다.
- `tricast.calibration._windows` 는 `random.Random(seed).randrange(n − seqlen + 1)` 로 시작 위치를 뽑는다.
- seed 42 표 창(512)과 seed 42 보정 창(2048)은 상한의 비트 길이가 같아서, 시작 위치가 사실상 같은 값으로 나온다.
- 그러면 표의 창이 보정 창 안에 들어간다.
- 결과적으로 보정 방법의 층별 KL 은 자기 보정 데이터 위에서 재지고, 풀이는 보정 방법 쪽으로 치우친다.

그래서 v2 의 표 · 측정 창은 validation split 에서 뽑는다. 보정은 Quantizer 기본값대로 train 에서 뽑는다.
- 판정 기준(C1~C4, C3′)은 바꾸지 않았다.
- 바꾼 것은 창의 출처뿐이다.
- v1 과의 보조 비교에는 "표 창의 split 이 다름"을 함께 적는다.

해석 주의 (결과와 무관하게 보고에 적는다):
- 크기는 가중치 비트만 센다. 8비트 층은 활성값도 8비트다.
- 표는 seqlen 512, PPL 은 2048 이다.
- 보정 방법의 활성값 형식은 NVFP4 (AWQ · SQ) 또는 없음 (GPTQ W4A16) 이라 활성값 비용이 방법마다 다르다.
