# 스파이크: CUDA core 에뮬레이션이 텐서코어 누산을 비트 단위로, LLM 평가에 쓸 만한 속도로 재현하는가

> 강의 4 지침의 여섯 절 구성을 따른다. 1~4절은 **실험 전** 에 작성했다: 파일 생성 2026-09-30 09:20 UTC
> (커밋 `64c10e3` 09:08 UTC 직후), NADPE 골든 벡터 생성 09:37 UTC (`tests/data/nadpe/manifest.json`).
> 5~6절은 실측 후 채운다. 성공 조건은 결과를 본 뒤 바꾸지 않는다.
> 팀 추인 (2026-10-01): 3절의 성공 조건을 고치지 않고 추인했다 (지침: 스파이크의 성공 조건은 사람이 정한다;
> 실측이 시작된 뒤라 추인과 무효 선언만 가능했다).

## 1. 가장 위험한 가정

**"Triton 으로 CUDA core 에서 돌리는 MMA 누산 에뮬레이션이 (a) 독립 구현(NADPE CUDA 커널)과 비트 단위로
같은 결과를 내고, (b) 0.6B 급 모델의 WikiText-2 전체 평가를 A100 1장에서 수십 분 안에 끝낼 만큼 빠르다."**

- 실패 영향: TriCast 의 핵심 가치는 "하드웨어 누산 구성을 바꿨을 때 LLM 품질이 어떻게 변하는지를 믿을 수 있게,
  빠르게" 보여 주는 것이다. (a)가 틀리면 결과를 믿을 수 없고, (b)가 틀리면 설계 탐색 루프에 쓸 수 없다.
- 근거 부족: 레퍼런스(순수 PyTorch 정확 연산)는 torch 네이티브 캐스트와 비트 일치를 확인했지만(커밋
  `64c10e3`), Triton 커널의 정수 비트 연산·시프트 가드·FTZ 회피가 GPU 에서 레퍼런스와 같은지는 아직 한 번도
  확인하지 않았다. 처리량도 추정치뿐이다.
- 대체 비용: 비트 일치가 안 되면 NADPE 처럼 CUDA C++ 로 커널을 새로 써야 하고, 새 파라미터 값마다 템플릿
  재컴파일이 필요해진다 (NADPE `design_space.cuh` 는 허용 값 집합을 컴파일 타임에 고정한다).
- 다른 후보와 비교: "HF/lm-eval 통합이 된다"는 가정은 표준 API 라 대체 비용이 낮고, "양자화 스킴이 정확하다"는
  microxcaling 오라클로 로컬에서 싸게 검증된다. 이 가정만 GPU 가 있어야 확인되고 틀렸을 때 비용이 가장 크다.

## 2. 시간 제한

1일 (최대 8시간의 작업 시간), GPU 는 A100 1~2장. 종료 조건은 8시간 경과 또는 3절의 두 측정 완료 중 먼저 오는
시점. 종료 시 결과와 무관하게 멈추고 그때까지의 결과로 판정한다.

## 3. 성공 조건 (실험 전에 확정)

검증 가능한 문장 두 개:

1. **비트 일치**: NADPE CUDA 커널(vLLM 없이 단독 빌드)로 만든 FP8 골든 벡터 전 케이스 — CoFDA fused/decoupled
   F ∈ {3,5,7,9,10,11,12,13,17,21,25} × CS ∈ {16,32}, GDFS F ∈ {7,13,25,35} × G ∈ {3,4,5,6,8,13,32} ×
   GS ∈ {8,16}, 입력 세트 2종 × shape 3종 × scale 2종 — 에서 TriCast Triton 출력(bf16)이 **100% 비트 일치**.
2. **속도**: Qwen/Qwen3-0.6B, `hopper_fp8_w8a8` 레시피(모든 decoder linear 를 CoFDA F=13 CS=32 로 에뮬레이트)
   로 WikiText-2 test 전체(seqlen 2048)의 PPL 평가가 **A100 1장에서 30분 이내**에 끝난다.

- 평가 단위와 건수: (1) 출력 원소 단위, 골든 벡터의 모든 원소. (2) 전체 평가 1회의 wall-clock.
- 건별 판정 규칙: (1) bf16 비트 패턴이 같으면 일치 (NaN 은 NaN 끼리 일치로 센다). 한 원소라도 다르면 그 케이스
  불일치. (2) 시작(모델 로드 후)~PPL 출력까지의 시간.
- 합격선: (1) 불일치 케이스 0. (2) ≤ 30분. 둘 다 만족해야 통과.

## 4. 방법 (성공 조건을 재는 데 필요한 것만)

1. 정답 만들기: NADPE MMA-Emu 원본 CUDA 소스(`micro26-ae/csrc/quantization/mma_emu`)를 수정 없이 단독 torch
   extension 으로 A100(sm_80)용 빌드하고, 고정 seed 무작위 FP8 입력으로 골든 벡터를 저장한다. 같은 설정 2회
   실행 비트 동일을 먼저 확인한다 (결정론).
2. 모델 출력 만들기: 같은 입력을 TriCast `gemm(..., backend="triton")` 으로 실행 (설정 고정, 1회).
3. 대조: 원소별 비트 비교, 불일치 케이스 수를 센다. 속도는 `tricast ppl` 1회 wall-clock.

이 밖의 일 (커널 튜닝, 코드 정리) 은 스파이크에서 하지 않는다.

## 5. 결과

모두 A100-SXM4-80GB (geneva), torch 2.8.0+cu128, triton 3.4.0. 시각은 UTC (2026-09-30).

**조건 1 — 비트 일치.** 스파이크 범위의 커널 (튜닝 전, 이후 커밋 `3b32b07` 에 들어간 그대로) 로
`scripts/nadpe_oracle/check_triton.py` 를 FP8 골든 벡터 전부에 돌렸다: 1200 케이스 (CoFDA fused 264,
C-decoupled 264, GDFS 672), **불일치 0** (14:28 이전에 로그에 기록). 판정 규칙대로 bf16 비트 패턴을 원소마다 비교했다.
같은 커널은 실제 크기 GEMM (2048×1024×3072, 2048×3072×1024, 4096³) 에서도 NADPE 와 비트 일치했다
(`scripts/bench/bench_mma_vs_nadpe.py`, 3 구성 × 3 크기).

**조건 2 — 속도.** 같은 커널로 `hopper_fp8_w8a8` 의 2048 토큰 창 하나가 **83.4 s** 걸렸다 (torch profiler,
`_gemm` 이 CUDA 시간의 99.93%). WikiText-2 test 는 146 창이므로 전체 평가는 약 3.4 시간으로 **30 분 합격선을
넘는다** — 전체 실행은 하지 않았고, 이 수치는 한 창 실측의 외삽이다. 같은 GEMM 의 처리량은 0.011 TMAC/s 로
NADPE CUDA 커널 (0.15 TMAC/s) 의 7% 였다.

**스파이크 이후 (판정에 넣지 않는 기록).** 4절에서 제외한 커널 튜닝을 이어서 했다. 원인은 산술량이 아니라
레지스터 스필이었다 (모든 타일 설정에서 스필 1000~6000). 유한 입력 전용 컴파일, 런타임 루프, int32 디코드 후
(커밋 `bb44ccd`): 처리량 0.15 TMAC/s (NADPE 대비 0.99~1.07 배), FP8 1200 + FP4 516 = 1716 케이스 불일치 0,
`tricast run` 으로 잰 `hopper_fp8_w8a8` 의 WikiText-2 전체 평가 **14.8 분** (PPL 21.2035, 패치 포함, 모델 로드
제외; 15:11 완료). 결과 기록은 `docs/results/qwen3_0.6b.md`.

## 6. 판단과 재도전 조건

- 조건 1 **통과**, 조건 2 **실패** → 3절 규칙상 스파이크는 **실패**다. 가정 (a) "독립 구현과 비트 단위로 같다"는
  성립했고, 가정 (b) "LLM 평가에 쓸 만한 속도"는 스파이크 범위의 구현에서 성립하지 않았다.
- 실패 원인은 알려졌다: 정확성 테스트가 성능 결함을 잡지 못했고 (연산 수가 아니라 스필), 설계는 바꿀 필요가
  없었다. 스파이크 이후의 14.8 분은 같은 조건 2 를 다시 잰 값이지만 4절의 범위를 벗어난 작업의 결과이므로
  판정을 뒤집지 않는다. 팀은 이 재측정을 새 스파이크의 결과로 추인했다 (2026-10-01).
- 재도전 조건: 커널이 바뀌면 (새 누산 알고리즘, 새 형식 계열) 같은 두 조건을 같은 규칙으로 다시 잰다.
  속도 회귀는 `scripts/bench/bench_mma_vs_nadpe.py` 의 NADPE 대비 비율 (현재 ≥ 0.97, GDFS G=32 는 0.69) 로 본다.
