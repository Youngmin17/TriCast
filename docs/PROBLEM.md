## 1. 한 문장 문제 ✍️

저정밀 모델과 NPU 연산기를 설계·검증하는 연구자와 엔지니어가, 비트 폭·스케일링·누산과 라운딩 방식·희소성·
이상치 처리 조합이나 GPU 세대를 바꿀 때마다 그 효과를 다시 구현하지 않고는 확인하지 못해, 조합마다 코드와
CUDA 커널을 새로 쓰고 검증한다 — 연구 본체보다 커널 유지보수에 더 많은 시간이 들 수 있고 (로그 10), 비교할
후보를 작은 모델·데이터셋으로 미리 줄인다 (로그 1).

## 2. 대상과 비대상 ✍️

- 1차 사용자: 양자화·저정밀도 학습을 직접 수행하는 연구자 (로그 1, 3), NPU 연산기 개발자 (로그 9),
  LLM 경량화 연구자 (로그 10)
- 비대상(현재): 모델을 ONNX 등으로 변환해 기기에 배포하는 엔지니어 — 변환·디바이스 호환성 문제(로그 2, 페인 2)는
  다루지 않는다. 경량화의 혜택을 기대하는 일반 사용자 (로그 5–8) — 전력·비용 절감은 이 제품의 간접 효과이지
  사용자가 아니다. 서빙 처리량을 최적화하는 엔지니어.

## 3. 증거

- 설정을 바꿀 때마다 코드를 다시 고치고 구현이 맞는지 확인한다 ("bit 수나 scaling 방법을 변경하면 관련 코드를
  다시 수정해야 했고, 제대로 구현됐는지 확인하는 데도 시간이 많이 걸렸습니다" — 로그 1, 페인 1)
- 연산 알고리즘·정밀도 조합과 GPU 세대가 바뀔 때마다 에뮬레이션 커널을 다시 만들고 검증한다 ("GPU 세대에
  따라서 커널 작업을 반복적으로 해야하고, 알고리즘 묘사와 정밀도 조합에 따라서도 마찬가지다" — 로그 9,
  페인 6, 7)
- 비트 폭·희소 비율·이상치 보존 방식 하나를 바꿀 때마다 CUDA 커널을 다시 깎는다 — 로그 10, 페인 7
- 하드웨어가 지원하지 않는 정밀도 연산을 알고리즘으로 우회 구현해야 하고, 속도·메모리 효율도 기대에 못
  미친다 (Hopper FP8 — 로그 3, 페인 3, 4)
- 공개 에뮬레이터도 허용 값 밖의 누산 파라미터는 C++ 수정과 재빌드가 필요하고, 36개 설정 스윕에 약 30시간이
  걸린다 (관찰 A1). 널리 쓰이는 MX 양자화 도구는 누산 산술을 모델링하지 않는다 (관찰 A2)
- 수요 신호 (사건 세부 없음 — 증거의 무게를 낮춰 본다): 병목·도구 필요 응답 (로그 4), 전력·인프라 비용
  절감과 접근성 기대 (로그 5–8)

## 4. 반증 조건 ✍️

- 문제 실재 — 인터뷰 전에 정한 조건 (2026-09-30)
  - 주장: 대상 사용자는 정밀도·누산기 결정을 LLM 수준 평가 없이 내리거나, 그 확인에 큰 왕복 비용을 치른다.
  - 반증 조건: 대상 10명 중 최근 6개월 안에 (a) LLM 품질 확인 없이 대리 지표만으로 결정했거나 (b) LLM 품질
    확인에 하루 이상 걸린 사례가 **3명 미만**이면 문제 정의를 기각하고 대상이나 문제를 다시 쓴다.
  - 판정 (2026-10-01): **기각** — (a)나 (b)를 말한 로그가 없다. 가장 가까운 로그 1 도 작은 모델·데이터셋으로
    후보를 먼저 줄인다고(페인 1) 했을 뿐 대리 지표만으로 결정했다는 진술이 아니고, "확인하는 데도 시간이 많이
    걸렸습니다"에는 기간이 없다. 조건에 따라 1절의 문제를 로그 1, 3, 9, 10 의 진술로 다시 썼다.
- 문제 실재 — 다시 쓴 문제 (2026-10-01)
  - 주장: 대상 사용자는 정밀도·연산 조합이나 GPU 세대를 바꿀 때마다 코드·커널을 다시 구현하고 검증을
    반복한다.
  - 같은 로그로 센 값 (이 주장이 이 로그에서 나왔으므로 독립 판정이 아니다): 실무 경험을 말한 5명(로그 1, 2,
    3, 9, 10) 가운데 다시 구현했다고 말한 사람 4명 (로그 1, 3, 9, 10). 검증 반복은 3명 — 로그 1 은 인용
    ("제대로 구현됐는지 확인하는 데도 시간이 많이 걸렸습니다"), 로그 9·10 은 팀이 정리한 페인 6 — 이고, 로그
    3 은 검증을 말하지 않았다. 로그 2 의 페인은 변환·디바이스 호환성이라 세지 않았고, 로그 4 는 사건 세부가
    없는 Y/Y/Y 응답이라 세지 않았다.
  - 반증 조건 (다음 인터뷰로 판정): 새로 만나는 실무 대상자 가운데 최근 실험에서 설정이나 하드웨어 조건
    때문에 코드·커널을 다시 작성하고 검증한 사례가 절반 미만이면 기각한다. 화면 관찰이 없어 지금은 진술만으로
    판정한다 (interviews.md C절).
- 해결 가설 (제품 사용 관찰로 이후 판정)
  - 가설: 정밀도·누산·희소성·이상치 조합을 레시피 값으로 바꾸면 실제 연산기와 비트 단위로 같은 산술로 모델
    품질과 누산 오차(ULP)가 나오므로, 조합을 바꿀 때 커널을 다시 작성하지 않아도 된다.
  - 반증 조건: 검증을 통과한(AC1·AC7) 레시피 결과를 받고도 사용자가 같은 조합을 자기 CUDA 커널이나 C 모델로
    다시 구현해 확인하는 행동이 계속 관찰되면 기각한다. 원하는 조합을 레시피로 표현할 수 없어서 다시 구현한
    경우는 가설이 아니라 범위(SPEC 4절)의 문제로, 에뮬레이션이 레퍼런스와 달라서 다시 확인한 경우는 정확성
    (AC1)의 문제로 따로 센다.

## 5. 성공의 정의 (행동 지표) ✍️

- 설계 조합 하나당 "레시피를 바꾼 시점 → 모델 품질과 ULP 수치를 받은 시점"까지 걸린 시간
- 실험 하나에서 비교한 설계 조합의 수 — 지금은 작은 모델·데이터셋으로 후보를 먼저 줄인다 (로그 1)
- 조합을 바꾸면서 사용자가 새로 작성한 커널·구현 코드의 양 — 0이 목표
