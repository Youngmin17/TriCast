# 위임 기록 — 이미지 생성 모델 예시 Z-Image-Turbo (2026-11-14)

> 이 기록은 구현을 맡은 Claude Code 세션이 작성한 초안이다. 팀 검토 · 추인은 아직 받지 않았다 (§5).

튜닝 화면에 세 번째 종류의 모델(이미지 생성)을 측정 기록으로 더하는 작업이다. 누가 무엇을 정했고, 무엇을 맡겼고, 맡긴 결과를
어떻게 다시 확인했는지 남긴다. 수치와 프로토콜은 [`docs/evidence/2026-11-14_zimage_turbo.md`](../evidence/2026-11-14_zimage_turbo.md)
에 있다.

| 역할 | 누구 |
|---|---|
| 요구 · 기준 확정 · 수용 판단 | Youngmin17 |
| 구현 · 클러스터 실행 · 문서 | Claude Code 세션 (Youngmin17 지휘), 커밋은 사람이 요청할 때만 |

## 1. 사람이 정한 것

| 결정 | 내용 |
|---|---|
| 요구 | "Z-Image-Turbo 도 추가해봐, v100 에서 가능하면" |
| 장비 | V100 (athens · london, `gpu_cap` 경유). A100 · H100 은 쓰지 않았다 |
| 화면 | 언어 모델은 생성한 답을 보이지 않지만(2026-11-13), 이미지 생성은 YOLO 의 검출 상자처럼 출력 비교를 보인다 |
| 테스트 | 기존 테스트 파일은 고치지 않고 새 파일 `app/tests/test_zimage_tune.py` 로만 |

| 시연 크기 추가 (2026-11-14, 첫 결과를 본 뒤) | "기존 방법은 잘 안되고 우리건 잘 되는 그런게 잘 안보이는데" → 계단 사이 크기 19% · 16% 를 더하기로 선택 (화면에는 5개 크기 모두, 기존 테스트 파일 `app/tests/test_zimage_tune.py` 수정 승인). 판정 규칙은 그 크기를 재기 전에 근거 문서 §5.1 에 씀 |

## 2. 맡긴 일과 성공 기준 (측정 전에 정함)

- **태스크**: `scripts/quantizer/zimage_tune.py` (refs · table · merge · solve · evaluate · export), 화면(`tune.js` 의 이미지 생성
  종류), 검사(`tune_models_check.mjs`), 문서.
- **성공 기준**:
  1. V100 에서 유한한 출력으로 돈다 (FP16 이 안 되면 그 사실과 대안을 기록).
  2. 표 · 해 · 평가 · 내보내기가 같은 조건(refs · 정밀도 · 방법 명세)에서 나왔음을 기록이 스스로 보증한다.
  3. 판정 규칙을 측정 전에 근거 문서 §1 에 쓰고, 화면은 판정과 무관하게 측정값을 그대로 싣는다.
  4. 내보낸 기록이 `validate()` 를 통과하고, 화면 검사(1440 · 390 px)가 통과하며 기존 모델 화면은 그대로다.
  5. `ruff check` 무경고, CPU · 앱 테스트 통과.
- **맡기지 않은 것**: 기존 테스트 · 골든 · evals 판정 기준의 변경, 커밋, 결과 해석의 최종 판단.

## 3. 검증 루프 — 단계별로 다시 돌린 것

| 단계 | 무엇으로 | 결과 |
|---|---|---|
| V100 첫 시험 | `zimage_probe` (athens) | FP16 은 512 · 1024 px 모두 latent 비유한 → FP32 로 결정. 텍스트 인코더가 GPU 에 남아 FP32 로드가 메모리 부족 → 인코더를 CPU 로 내리고 확인하게 고침 |
| refs 첫 실행 | 단계 수 검사 | 프롬프트 4개에 forward 36번 (프롬프트당 9) → diffusers 0.39 의 기본 시그마에서는 `num_inference_steps=8` 이 8번 호출임을 확인, 8 로 고침 |
| 원본 정밀도 | 체크포인트 전수 검사 (monaco CPU) | FP32 텐서 521개가 모두 BF16 값 → "BF16 유지" 를 16비트 · 오차 0 으로 두는 근거 |
| 표 첫 실행 | athens 두 작업 동시 로드 | 엄격한 커밋 한도로 `MemoryError` → 가중치를 GPU 로 바로 올리게 고침 |
| 교차 검토 | Codex 읽기 전용 | 10건 (MAJOR 7 · MINOR 3) → §4 |
| 재검토 | 같은 엔진, 고친 부분만 | 8 해결 · 2 부분 · 새 3건 → 모두 고침 (근거 문서 §1.6) |
| 화면 | 가짜 기록(실제 275층 형상, 임의 수치)으로 정적 서버에서 미리 검사 | 이미지 생성 항목 11/11 (1440 · 390 px), 기존 3모델 34/34 그대로 |
| 테스트 | `app/tests/test_zimage_tune.py` (클러스터 CPU) | 18 passed (실제 크기 배낭 · FP32 정확 복원 · 지문 · 검증기 포함) |
| 층별 표 | athens GPU 2장 × 2회, 275층 × 4방법 | 모든 값 유한 · 층 번호 연속, 비트 순서를 어긴 층 1개 (근거 문서 §4), 층 측정 9.75 GPU·h |
| 배낭 | HiGHS 의 하한과 해의 값 | 3개 모두 차 ≤ 1e-16, 비용은 정수로 다시 확인 |
| 평가 | 8셋업 × 프롬프트 24개 | 후반부 첫 시도가 같은 노드 동시 실행으로 메모리 부족 → 앞부분 뒤에 같은 명령으로 다시 (결과 파일을 쓰기 전에 멈춤) |

## 4. 교차 검토에서 나온 결함과 처리 (모두 표의 첫 행을 쓰기 전)

| 지적 | 처리 |
|---|---|
| INT4 · 3 · 2 의 복원이 BF16 반올림을 거침 (INT8 과 경로가 다름) | 모든 방법을 FP32 복원으로 명시, (q − z)·s 와 비트 대조 테스트. 이미 쓰인 표 두 행은 버림 |
| "FP16 유지" 의 비용 · 오차 정의 | 원본이 BF16 값임을 전수 확인하고 "BF16 유지" 로, 로드마다 확인 |
| 실제 크기에서 정확 DP 가 안 풀림 (5.5e10 칸) | 정수계획(HiGHS)으로 풀고 비용을 정수로 다시 확인, 해의 하한과의 차를 기록 |
| 결과를 보고 고른 비교 상대로 p 값 | 측정 전에 정한 짝 · Holm 보정 |
| 재개 · 합치기 · 평가 재사용이 다른 조건의 행을 섞음 | 실행 지문을 첫 행 전에 쓰고 모든 단계에서 대조 |
| D 가 FP32 에서 넘칠 수 있음 · NaN 이 JSON 에 | FP64 합산 · 유한성 검사 · `allow_nan=False` · 검증기 |
| 화면 · 검사의 원본 지표 · PSNR null 처리 | 원본 지표 {SSIM 1, PSNR 없음}, null = 같은 이미지 |
| 예시 3장을 판정에서 뺀다는 문장 | 판정 24개에 포함된다고 고침 |
