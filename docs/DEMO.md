## 1. 대상 사용자와 문제 (1분)

> 양자화 방법과 레이어별 정밀도를 정해야 하는 엔지니어가, 방법 · 레이어 조합을 바꿀 때마다 코드를 다시 짜고 모델 전체를 다시 평가해야 해서, 원하던 조합의 일부(30개 이상 중 6개)만 평가하고, 레이어별 혼합 정밀도를 손으로 전수 탐색하는 데 3주~3개월을 쓴다. ([PROBLEM §1](./PROBLEM.md#1-한-문장-문제))

- 성공의 정의 ([PROBLEM §5](./PROBLEM.md#5-성공의-정의-행동-지표)): 레이어 배정 확정 3개월 → **1주 이내** (S3), 조합을 바꿀 때 코드 재작성 **0회** (S4), 공유 결과의 실행 환경 동반 **100%** (S5).
- 한 줄로: "196개 층 × 16개 방법 = 16^196 조합. 사람은 이걸 손으로 못 고른다. TriCast 는 크기 예산 하나로 고르고, AI 가 측정 근거로 고친다."

## 2. 핵심 시나리오 — 한 화면 6박자 (5분)

한 화면(`tune.html`)에서 모델을 넣고, 목표 크기를 골라 추천을 받고, 직접 바꿔 보고, 평가한다. 화면의 품질 숫자는 모두 그 셋업의 GPU 측정 기록이고, 레시피 파일은 지금 서버가 만들어 측정한 파일과 지문(SHA-256)을 대조한다. AI 의 세부 설정은 AI 튜닝 세션(11월 4일)이 GPU 로 잰 것 중 PPL 이 좋아진 것만 추천에 들어간다 — 27% 크기처럼 더 나빠진 곳에서는 쓰지 않았다고 적힌다. 직접 편집은 지금 GPU 로 재 둔 조합(전체를 한 방법으로 · 세부 설정)만 고를 수 있다. 이 PC 에 GPU 가 없으면 평가는 그 셋업의 A100 측정 기록을 보여 주고, GPU 서버(`--live`, CUDA)에서는 같은 버튼이 레시피 파일 그대로 PPL · lm-eval 을 실제로 돌린다.

**[고지]** "지금 실제로 도는 것은 배낭 계산(브라우저)과 레시피 파일 생성 · 지문 대조(서버)입니다. 층별 오차 표(A100 에서 5.7시간), AI 가 찾은 세부 설정, 품질 숫자는 A100 측정 기록입니다."

### 2-1. 선택 박자 — 다른 모델에서 기존 방법 vs 우리 방법 (여유 시간 · 질의 때)

① 의 모델 목록에서 고른다. 두 모델 모두 **기록 재생**이다 (이 PC 에서 다시 재지 않는다). 기존 방법 = 모든 층에 한 방법(YOLO 는 흔한 규칙 "가장자리 INT8 + 나머지 INT4" 도), 우리 방법 = 같은 크기 안에서 Auto-tune 이 층마다 고른 배정. 두 모델 모두 AI 튜닝 세션은 없다 (② 의 이유 줄이 "층별 자동 배정" 하나).

## 4. 장애 대응

| 상황 | 대응 |
|---|---|
| 서버가 뜨지 않음 | `python -m app.server --demo` (`--agent` 없이) — 모든 숫자와 평가는 그대로 나오고, AI 세부 설정의 레시피 파일만 `--agent` 서버에서 받는다고 안내된다 (한 방법 편집의 파일은 나온다) |
| 브라우저를 실수로 새로 고침 · 닫음 | 주소(`#model=…&size=…`, 편집했으면 `&uniform=…` 또는 `&option=…`)에 작업이 남아 같은 셋업 · 같은 레시피 파일로 이어서 열린다 — 평가만 다시 누른다 |
| 네트워크 끊김 | 화면은 네트워크를 쓰지 않는다 (글꼴만 기본 글꼴로 바뀐다). 서버까지 안 되면 예비 녹화 GIF |
| 질의에서 "AI 가 휴리스틱보다 낫나?" | 지금 근거: 데모 세션에서 AI 가 휴리스틱 해를 같은 비트로 검증 KL −11.4%, held-out test PPL 은 보정 seed 5개 평균 −3.48% (5/5 seed, p = 1/32, 차이가 seed 범위보다 큼) 더 낮췄다. 같은 옵션을 다른 예산의 휴리스틱 해에 옮기면 2.5 비트 PPL 465 → 133, 3.0 비트 32.4 → 30.2 이고, 3.5 비트 이상에서는 잡음 수준이다 (2.5 · 3.0 비트는 보정 seed 5개 모두에서 낮고 평균 −64% · −7.7%, p = 1/32). 반대로 AI 옵션 아래 배낭을 다시 푼 재배정은 예측과 달리 검증 KL 이 1.7% 나빠졌다 — 이득은 표가 다루지 않는 옵션 축에서 나오고, 표 위의 칸 배정은 휴리스틱이 이미 잘 한다. 모델 하나라 확정은 아니다. AI 가 같은 측정 수에서 강한 탐색 기준선보다 낫다는 주장(H2)은 사전 등록 실험에서 판정한다 — 아직 주장하지 않는다. |

## 5. 예상 질문

- **왜 층 하나씩 잰 KL 의 합을 쓰나?** 국소 SQNR 은 모델 품질 순위를 못 맞췄다 ([스파이크](./spikes/2026-10-13_layer_sqnr_proxy.md)). 합은 4비트 근처에서 실측을 과대평가하고 3비트 아래에서 과소평가한다 — 그래서 측정 루프가 있다.
- **AI 가 틀린 숫자를 쓰면?** 제안이 기록되기 전에 거부된다 (AC24: 인용 레코드 실존, 적힌 자릿수의 수치 지지). 라운드 1 이 그 예다.
- **층 하나를 내 마음대로 두면?** 격자 칸에 올리면 그 층의 방법과 그 층만 바꿨을 때의 오차(KL)가 나온다. 층 하나씩 바꾸는 편집은 그렇게 만든 셋업의 측정 기록이 없어 지금은 열지 않았다 — 직접 편집은 GPU 로 재 둔 조합(전체를 한 방법으로 · 세부 설정)만 고른다. 제약(블록을 BF16 으로 유지 등)을 건 배낭은 `app.autotune solve` 로 만들 수 있고, 그 셋업은 GPU 로 잰 뒤 화면에 올린다.
- **표 한 장은 얼마나 걸리나?** Qwen3-0.6B 196층 × 16방법, A100 5.7시간 (한 번). 배낭은 초 단위, 라운드는 Claude 1–4분 + 측정 수 분.
- **칩 연산 비용은?** 트랙 C 연산 예산(B200 처리량 비 FP4:FP8=INT8:BF16 = 4:2:1, NVIDIA 사양)으로 비트와 함께 묶는다 (`solve --compute-budget`).
