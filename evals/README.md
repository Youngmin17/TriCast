# Request parsing evaluations

These are **human-review criteria**, not labels generated by running the parser.
The team approved the requests, field annotations, metric denominators and judge
rubric on 2026-10-01.

The product criteria are [SPEC §6](../docs/SPEC.md#6-수용-기준-ac-ears--조건일-때-tricast-는-동작한다-️);
numerical semantics are defined in [ENGINE](../docs/design/ENGINE.md).
The [golden cases](../tests/harness/golden_cases.yaml) cover AC1–AC7 separately:
hand-derived casting/quantization/MMA, invalid recipes, provenance, saved evaluation
metadata, missing parser parameters, independent NADPE vectors, and GPU bf16 PPL.
Passing CPU arithmetic cases alone does not establish Triton parity or full-model quality.

## What is measured

`run_evals.py` calls `parse_request(text, llm=...)`. It does **not** execute the
resulting recipes, download HF models, or score generated final answers.

| Metric | Numerator / denominator | Why |
|---|---|---|
| `schema_valid_rate` | Requests whose `request.to_dict()` validates against `emulation_request.schema.json` / all requests | Structured data must obey the public contract. |
| `field_accuracy` | Exact matches / all annotated `expected` fields | Checks extraction of explicitly stated intent, model, arithmetic, and tasks. |
| `invention_rate` ↓ | Non-null `must_be_null` fields without a matching assumption / all annotated `must_be_null` paths | AC6: missing precision or accumulation parameters must not silently become facts. |
| `ambiguity_recall` | `ambiguous=true` requests with at least one nonblank question / all `ambiguous=true` requests | AC6: unresolved choices and explicit clarification requests must be surfaced. |

Field and null-path rates are **micro-averages**, not averages of per-request
percentages. Missing parents/array elements count as unfilled for invention checks.
An absent field is not an exact match for an explicitly expected `null`. Arrays are
order-sensitive; object key order is irrelevant; JSON booleans are not numeric 0/1.
An explicit non-null value, including 0, false, or an empty collection, is filled.
A zero denominator produces JSON `null` and table `N/A`, never a perfect score.

A parser exception or `request=None` stays in the denominator: schema and expected
fields fail, and an ambiguous request has no successful clarification. Such failures
can lower invention counts, so **never interpret invention rate alone**. Parse errors
and schema errors are recorded separately; a schema-valid response can still contain
semantic errors. Anthropic parser error details are omitted because provider exception
messages can contain credentials; raised exceptions retain only their class name.

### Annotation conventions

Each JSONL line is one request, including `_draft`, `id`, `language`, `difficulty`,
`text`, `expected`, `must_be_null`, `ambiguous`, and a rationale in `note`.
The draft notice is the first JSON field, not a comment that would break JSONL.

`expected` maps full field paths to hand-labelled values, for example:

```json
{"intent": "evaluate", "recipes[0].mma.f_bits": 13, "tasks": ["hellaswag"]}
```

Paths use zero-based brackets (`recipes[0].mma.g_bits`), matching the request schema,
not the resolved `Recipe.defaults` layout. Only certain fields are scored; recipe
names synthesized by the parser are deliberately not labelled. Every rationale
explains which text warrants the label. F and G are distinct, and an operand scheme
does not identify the MMA hardware preset.

`must_be_null` means **unfilled or explicitly recorded as an assumption**, not an
unconditional ban on defaults. To exempt a filled field, the current string-valued
`assumptions` must name its exact full path; a generic “defaults applied”, a leaf such
as `f_bits`, or a parent path does not exempt it. The scorer also supports an exact
`{"path": "..."}` entry in synthetic unit fixtures; the production request schema
currently requires strings. This attribution convention is a draft evaluation rule,
not a change to the product schema. It does not verify the truth of an assumption.

`ambiguous=true` requires a question even if a default is recorded. This distinguishes
“missing and safely defaultable” from “the user explicitly asks us to clarify”.

## Running

From the repository root, with the package and `jsonschema` installed:

```bash
PYTHONPATH=src .venv/bin/python evals/run_evals.py --llm offline
PYTHONPATH=src .venv/bin/python evals/run_evals.py --llm offline --limit 3
PYTHONPATH=src .venv/bin/python evals/run_evals.py --llm offline --out evals/results/YYYY-MM-DD.json
```

`--limit N` takes the first N records in file order, not a balanced sample. The CLI
prints all four metrics; `--out` additionally writes counts, per-field comparisons,
invented paths, questions, sources, parse/schema errors, and parsed requests.
An existing output is rejected before parsing; choose a new filename rather than
overwriting evidence. Without `--out`, no result file is saved.

For paid parsing, install the agent's Anthropic SDK dependency and provide an
existing `ANTHROPIC_API_KEY` environment variable. Do not place keys in this repo,
the dataset, logs, or results. A missing key exits with an actionable message.

```bash
PYTHONPATH=src .venv/bin/python evals/run_evals.py --llm anthropic --limit 1
PYTHONPATH=src .venv/bin/python evals/run_evals.py --llm anthropic --out evals/results/YYYY-MM-DD.json
```

**Cost:** 30 requests × 1–3 parser attempts means up to 90 provider calls, plus any
SDK retries. Start with `--limit 1`. Costs depend on model and token usage; the runner
neither estimates charges nor places a monetary cap. It never silently falls back
to offline in `--llm anthropic` mode. Do not run paid evaluations as an ordinary test.

## Evidence and review

Record reviewed runs as `results/YYYY-MM-DD.json`. If comparing multiple runs that
day, use distinct suffixes rather than replacing a previous result. Each result
contains the git SHA and dirty flag at the start, requested parser/model name,
UTC start/end times, and SHA256 of the exact evalset and schema snapshots used.
`TRICAST_AGENT_MODEL` selection is read from the parser's `request_options()` rather
than copied into a second default in this script.

A provider-side fallback may use a different model: `model_is_requested=true`
means the recorded model is the requested one, **not** a verified response model.
The current ParseResult API does not expose the actual provider model or token cost.
A dirty SHA does not fully identify uncommitted implementation files; archive the
reviewed patch/environment separately before publishing comparisons. Do not compare
scores with different evalset hashes as if they measured the same task.

Review `per_item`, not just the table. The offline end-to-end unit test checks all
30 records for wiring/schema validity, not a fabricated 100% semantic target. No
quality threshold has been team-approved yet. Run the regression gates separately:

## Limits and team decisions

- Thirty synthetic requests are too small for generalization claims; add reviewed
  real requests without replacing failing labels with parser output.
- Exact matching penalizes equivalent representations and order changes. The
  schema and annotation convention must be reviewed together.
- Invention rate checks only labelled paths and whether assumptions name them. It
  does not certify all output fields, default appropriateness, or truthfulness.
- Ambiguity recall checks question presence, not relevance, and does not measure
  unnecessary questions on clear requests.
- Deterministic offline parsing is not evidence of paid-provider reliability. Paid
  results can vary and must record their own artifacts.
- [The judge rubric](judge_prompt.md) evaluates final-answer grounding separately.
  LLM judging is advisory; disagreements require human review.
- The team approved the golden values and notes, request annotations, exact-path
  attribution and dataset balance on 2026-10-01. A pass/fail threshold is not set yet.
