# TriCast: 3분 발표 시나리오

**한 문장:** “수 형식·누산 산술·희소성·이상치 처리를 레시피의 값으로 바꾸면, 커널을 다시 쓰지
않고 같은 모델에서 그 선택이 품질과 누산 오차에 미치는 영향을 GPU 한 장으로 비교합니다.”

**누구의 문제인가:** 팀 인터뷰 10건 가운데 실무자 5명 중 4명이 설정이나 하드웨어 조건이 바뀔 때마다
코드나 커널을 다시 구현한다고 말했다 (로그 1, 3, 9, 10 — `docs/research/interviews.md`, `docs/PROBLEM.md`).

실행법은 [examples/README.md](../../examples/README.md), 수치 의미론의 기준은
[ENGINE.md](../design/ENGINE.md)입니다. 아래 3분은 **발표 시간**입니다.
전체 평가가 3분에 끝난다는 실측 주장이 아닙니다.

## 사전 준비

1. GPU 운영자가 한 슬롯을 배정한 뒤 다음 명령을 실행합니다.
   모델·WikiText-2 다운로드와 Triton 첫 컴파일은 발표 전에 끝냅니다.

   ```bash
   PYTHONNOUSERSITE=1 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
     /scratch/uceeeee/conda_envs/tricast/bin/python examples/demo_qwen3.py --quick
   ```

   Triton 캐시가 준비된 A100 한 장에서 약 40분 걸렸습니다 (아래 실측, 2026-10-01; 같은 노드에서 다른
   측정과 함께 돌았다).
2. `DEMO_DONE` 마커, `results.json`의 전체·행별 상태와 `report.md`를 확인합니다.
   실패한 행을 성공 사례로 읽지 않습니다. 시간 예산이 부족하면
   `--max-windows 2`로 리허설하되, 발표 표에 실제 윈도우 수를 밝힙니다.
3. `env.json`에서 소스 SHA/dirty 여부, 모델 commit, GPU, 패키지 버전, seed와
   데이터셋 fingerprint를 확인합니다. 원본 가중치 복원 검증과 패치된 모듈의
   forward 호출 기록도 확인합니다. 이 기록은 **커널 bit-exact 검증을 대체하지 않습니다**.
4. GPTQ 레시피(`w4a16_g128_zp_gptq`)는 평가 전에 `tricast.calibrate`로 WikiText-2 train
   512토큰 × 32개를 보정합니다 (`--calib-samples`, `--calib-seqlen`). `--skip-gptq`는
   리허설 시간을 줄일 때만 쓰고, 그때는 표에서 GPTQ 행이 빠집니다.

아래 **실측**은 모두 한 번의 실행입니다: NVIDIA A100-SXM4-80GB, 커밋 `a1b0ede` (clean),
Qwen3-0.6B `c1899de`, bf16, seed 42, torch 2.8.0+cu128, triton 3.4.0. 원본은
`runs/demo_quick_r7/{report.md,results.json,env.json}`입니다. 노드의 GPU는 다른 사용자의 작업과
공유되고 있었으므로 시간 열은 이 조건의 관측치입니다.

## 0:00–0:25 — 문제와 입력

**화면:** 실행 명령, 모델 이름, `report.md`의 환경 요약.

**말할 내용:** “인터뷰에서 들은 말로 시작합니다. ‘비트 폭 하나 바꾸고, 희소 비율 하나 틀고, 이상치
보존 방식 하나 수정할 때마다 CUDA 커널을 다시 깎아야 합니다’(로그 10). FP8이라는 이름만으로 덧셈
과정은 정해지지 않습니다. TriCast는 원소 형식, 스케일, 누산 알고리즘, 희소성, 이상치 처리를 레시피의
값으로 분리합니다. 오늘은 같은 Qwen3 가중치에서 이 선택들을 바꿔 봅니다.”

**범위:** 기본 모델은 `Qwen/Qwen3-0.6B`, BF16 로드, seed 42.
하드웨어 프리셋 이름은 **에뮬레이션할 산술**을 뜻하며, 해당 GPU에서 네이티브
텐서코어를 실행했다거나 실리콘과의 일치가 검증됐다는 뜻이 아닙니다.

## 0:25–1:00 — 형식 한눈에

**화면:** `formats` 표. 같은 `q_proj` 가중치를 BF16, FP8, MXFP8/6/4,
NVFP4/4o6, MSFP12, INT4로 바꾼 결과입니다.

**메시지:** “원소당 비트를 줄일 때 어떤 오차를 지불하는지 보입니다.
스케일도 저장해야 하므로 FP4라는 이름이 총 4비트 비용을 뜻하지는 않습니다.”

- SQNR(dB)는 `10 log10(Σw² / Σ(w−ŵ)²)`: 높을수록 이 가중치의 복원 오차가 작습니다.
  오차가 정확히 0이면 `inf`이며 누락값이 아닙니다.
- 최대 절대 오차는 가장 크게 달라진 한 원소의 크기입니다. 평균 품질 지표가 아닙니다.
- 비트/원소는 **논리적 형식 payload**입니다. 원소 수 × 형식 비트 + 실제 스케일 개수 ×
  스케일 비트 + global scale 32비트 + zero-point 비트를 원소 수로 나눕니다.
  마지막 짧은 그룹도 스케일 하나를 셉니다.
- 정수 zero point는 원소 형식 폭, 실수 zero point는 FP32라는 저장 가정을 씁니다.
  `UE4M3`는 현재 계약의 unsigned 7비트를 사용합니다. 실제 NVFP4의 8비트 스케일
  컨테이너나 PyTorch의 FP32 저장 메모리, padding, 패킹 효율을 주장하는 표가 아닙니다.
  `msfp12`도 이름의 숫자가 아니라 계약의 원소/공유 지수 비트로 계산합니다.

**실측** (`model.layers.0.self_attn.q_proj`, [2048, 1024]):

| 형식 | SQNR (dB) | 최대 절대 오차 | 논리 비트/원소 |
| --- | ---: | ---: | ---: |
| BF16 | inf | 0 | 16 |
| FP8 E4M3, 텐서당 스케일 | 31.54 | 0.0223 | 8.00 |
| MXFP8 E4M3 | 30.53 | 0.0527 | 8.25 |
| MXFP6 E3M2 | 25.33 | 0.0586 | 6.25 |
| MXFP4 | 18.70 | 0.1152 | 4.25 |
| NVFP4 | 20.46 | 0.0790 | 4.44 |
| NVFP4, Four-over-Six | 21.21 | 0.0790 | 4.44 |
| MSFP12 | 18.56 | 0.0625 | 4.50 |
| INT4, 128개 그룹 + zero point | 19.58 | 0.0408 | 4.16 |

원소가 4비트인 행끼리도 스케일 방식에 따라 SQNR가 18.6–21.2 dB로 갈립니다. 이 한 레이어의
순서입니다. 형식마다 품질 순서가 반드시 정해져 있다고 말하지 않습니다.

## 1:00–1:40 — 같은 FP8, 다른 누산

**화면:** `accumulation` 표에서 FP64 기준, Blackwell/Hopper/Ada 프리셋,
Hopper 기반 `F=7 fused`와 `F=7 decoupled` 행을 비교합니다.

**메시지:** “입력과 가중치의 양자화 값은 고정했습니다. 이제 바뀌는 것은
누산 산술입니다. F=7에서 부분합을 계속 같은 정밀도로 합칠지, F2=23의
분리된 누산기에 모을지 선택할 수 있습니다.”

- 짧은 프롬프트로 11번째 `mlp.down_proj`의 입력을 hook으로 받습니다.
  작은 모델에서는 마지막 레이어를 사용합니다.
- 앞 4개 입력 행 × 앞 32개 출력 채널만 사용하지만 K 축은 자르지 않습니다.
  두 부분행렬 자체를 FP8 per-tensor로 한 번 양자화해 모든 프리셋에 재사용합니다.
  **전체 레이어 출력 또는 전체 모델의 오차가 아닙니다.**
- 상대 Frobenius 오차는 `‖Y−Yref‖F / ‖Yref‖F`. 기준은 같은 양자화 피연산자의
  FP64 누산 후 FP32 출력입니다. 원래 비양자화 가중치와의 오차가 아닙니다.
- BF16 비트 불일치 비율은 두 FP32 출력을 BF16으로 변환한 뒤 16비트 패턴을
  비교한 원소 비율입니다. 0이면 이 표본에서만 같다는 뜻입니다.
- 시간은 CUDA-core 에뮬레이션 경과 시간입니다. warmup 3회, 측정 5회;
  p99는 5개 표본의 선형 보간값일 뿐 안정적인 tail-latency 추정이 아닙니다.

**실측** (`model.layers.10.mlp.down_proj` 입력 4행 × 출력 32채널, K = 3072):

| 누산 | 상대 Frobenius 오차 | BF16 비트 불일치 비율 | 최대 ULP (fp32) | 평균 ULP (fp32) | 중앙값 ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| FP64 (기준) | 0 | 0 | 0 | 0 | 1.13 |
| Blackwell FP8, F=25 | 4.7e-7 | 0 | 188 | 6.2 | 1.01 |
| Hopper FP8, F=13, 32개 묶음 | 2.0e-3 | 0.297 | 1,941,795 | 39,308 | 0.95 |
| Ada FP8, F=13, 16개 묶음 | 2.0e-3 | 0.289 | 1,578,625 | 35,857 | 1.19 |
| Hopper 기반 F=7, fused | 0.158 | 1.000 | 2,048,346,067 | 18,041,400 | 0.95 |
| Hopper 기반 F=7, decoupled | 7.8e-3 | 0.742 | 5,659,930 | 189,391 | 1.01 |

같은 F=7에서 누산값을 묶음마다 함께 절단하면(fused) 상대 오차가 0.158, 23비트에 따로
모으면(decoupled) 0.0078로 20배 차이입니다. 이 128개 출력에서의 값이며, 누산 순위를
일반화하지 않습니다. ULP 는 FP64 결과와 fp32 칸으로 몇 칸 떨어졌는지입니다 (로그 9 태그 `ULP오차`).
출력이 0 근처로 상쇄되면 fp32 칸이 촘촘해져 최대값이 크게 튀므로 평균과 함께 봅니다. 모델 전체
레이어를 bf16 출력 기준으로 잰 값은 결과 문서의 "Accumulator error in ULPs" 표에 있습니다. 시간은
에뮬레이터 시간이며 하드웨어 속도가 아닙니다. 행이 16개 이하라 FP8 행들은 작은 M 전용 커널로 돌고
(FP64 기준 행은 아님), 이 커널이 들어가기 전에는 같은 A100 에서 같은 행들이 2.52–2.62 ms였습니다
(`032684b` 데모 실행의 중앙값).

## 1:40–2:15 — 모델 품질로 연결

**화면:** `quality` 표의 PPL, 레시피, 경과 시간과 실제 윈도우 수.

**메시지:** “작은 행렬의 오차만으로 모델 품질을 단정하지 않고,
같은 WikiText-2 토큰에서 레시피별 PPL을 비교합니다.”

- PPL은 낮을수록 이 데이터의 다음 토큰을 더 잘 예측합니다. 모델·토크나이저·
  데이터 fingerprint·윈도우 수가 같은 행만 비교합니다.
- quick은 앞 16개 완전한 2048-token 윈도우까지입니다. 윈도우의 첫 토큰과
  마지막 불완전 윈도우는 채점하지 않습니다. 전체 test PPL로 부르지 않습니다.
- `bf16_passthrough`는 레시피가 정의한 누산 기준입니다. 네이티브 HF GEMM과
  bit-exact하다고 가정하지 않습니다. 생성 표의 `native`는 패치하지 않은 모델입니다.
- 레시피마다 unpatch → patch → 실행 → unpatch를 수행하고, 모든 원본 Linear의
  weight/bias 해시와 모듈 동일성을 확인합니다. 검증 실패는 해당 행을 실패로 표시합니다.
- 경과 시간은 패치·평가·복원 검증까지 포함한 **1회 관측치**로, 속도 우열의 근거가 아닙니다.

**실측** (앞 16개 윈도우, 채점 토큰 32,752개):

| 레시피 | PPL | 경과 s |
| --- | ---: | ---: |
| `bf16_passthrough` | 20.19 | 18 |
| `hopper_fp8_w8a8` | 20.40 | 168 |
| `fp8_f7_lowacc` (F=7, fused) | 27.58 | 162 |
| `fp8_f7_decoupled` | 20.51 | 169 |
| `mxfp8_w_a` | 20.50 | 382 |
| `mxfp4_w_a` | 31.78 | 237 |
| `nvfp4_w_a` | 25.05 | 229 |
| `nvfp4_4o6` | 24.38 | 260 |
| `nvfp4_outliers` (크기 상위 0.5% 를 bf16 으로 보존) | 25.12 | 257 |
| `fp8_2of4_sparse` (재학습 없는 2:4 가지치기) | 47,112 | 163 |
| `w4a16_g128_zp_gptq` (보정 포함) | 21.52 | 278 |

위 누산 표의 F=7 fused/decoupled 차이가 모델 수준에서도 27.58 대 20.51로 나타납니다.
아래 두 행은 로그 10 이 말한 "희소 비율"과 "이상치 보존 방식"을 레시피 한 줄(`sparsity`, `outliers`)로
바꾼 결과입니다. 재학습 없이 모든 linear 를 크기 기준 2:4 로 자르면 이 0.6B 모델은 무너집니다.
TriCast 를 거치지 않고 PyTorch 로 같은 2:4 를 직접 적용해도 같은 값이 나오므로 (앞 4개 윈도우에서
둘 다 73,434) 구현이 아니라 가지치기 자체의 결과이고, 실제 2:4 워크플로는 재학습을 포함합니다.
크기 상위 0.5% 를 bf16 으로 보존한 NVFP4 는 이 16개 윈도우에서 보존하지 않은 NVFP4 와 거의 같고
(25.12 대 25.05), test 전체에서는 조금 낫습니다 (26.18 대 26.22) — 크기로 고른 이상치 보존의 효과는
이 모델에서 작습니다.
146개 윈도우 전체의 결과는 [docs/results/qwen3_0.6b.md](../results/qwen3_0.6b.md)에 있습니다.

## 2:15–2:45 — 생성 비교

**화면:** `generation` 표. 한국어·영어 프롬프트 각각에 대해 native BF16,
Hopper FP8, FP8 F=7 fused, MXFP4 결과를 옆으로 보여줍니다.

**메시지:** “숫자 차이가 실제 출력 문장에도 나타나는지 직접 확인합니다.
다만 두 문장은 벤치마크를 대체하지 않습니다.”

같은 chat template, `enable_thinking=False`, greedy(`do_sample=False`, beam 1),
최대 48개 신규 토큰을 사용합니다. EOS로 일찍 끝나거나, 제한에 의해 문장이
잘리거나, 모든 설정이 같은 답을 내놓을 수 있습니다. 차이를 억지로 만들지 않습니다.
`--dtype`를 바꿨다면 `native`의 실제 dtype도 함께 밝힙니다.

**실측** (48토큰에서 잘린 문장 그대로):

| 설정 | 한국어 프롬프트: “양자화가 무엇인지 고등학생에게 두 문장으로 설명해 주세요.” |
| --- | --- |
| native | 양자화는 물리적 현상에서 입자의 위치와 운동량이 동시에 존재하는 상태를 말합니다. 예를 들어, 양자 입자가 고전적 이론에서의 고정된 위치와 운 |
| Hopper FP8 | 양자화는 물리적 현상에서 발생하는 특성입니다. 예를 들어, 양자화된 입자가 특정 위치를 가질 수 없고, 특정 위치를 가질 수 있는 상태를 양자 |
| FP8, F=7 fused | 양자화는 물리학에서 물리적 입자(예: 전자, 입자)가 고전적 상태(가장 빠르한 상태)를 유지하는 데서 시작됩니다. 예를 |
| MXFP4 | 양자화는 양자(자)의 상태를 나타내는 개념입니다. 양자화된 시스스에서는 양자들이 서로 다른 상태를 유지하면서, 이 상태를 바꾸는 것은 가능합니다 |

네 설정 모두 “양자화”를 물리학의 양자화로 읽습니다 (0.6B 모델 자체의 한계).
F=7 fused와 MXFP4에서 “빠르한”, “시스스” 같은 깨진 단어가 나옵니다. 영어 프롬프트
(“Explain in two sentences why an accumulator's precision matters in a dot product.”)에서는
네 설정 모두 문법에 맞는 문장을 씁니다. native·Hopper·F=7은 48토큰 제한에 걸려 둘째 문장
중간에서 잘리고, MXFP4는 한 문장으로 끝납니다. 전문은 `report.md`에 있습니다.
