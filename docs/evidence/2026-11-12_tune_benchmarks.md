## 1. 무엇을, 어떻게 읽는가 (측정 전에 정함)

### 1.1 벤치마크 (언어 모델, `scripts/quantizer/tune_bench.py` 의 `BENCHMARKS`)

| 묶음 | 벤치마크 | 지표 | 예제 | 문항 |

- 문항 상한의 이유: 레시피를 적용한 8B 의 fp32_fma GEMM 에뮬레이션은 H200 에서 약 620 토큰/초다
  (2026-11-12 탐색 실행: 2048 토큰 창 8개에 31.4 s, 같은 창의 BF16 은 1.8 s). 전체 세트(MMLU 5-shot 포함)는 셋업마다
  2.5–4 시간이라, 셋업 7개를 하루 안에 재려고 lm-eval 의 `limit`(과제 앞에서부터 N 문항, 결정적)를 썼다.
  화면은 문항 수와 전체 수를 함께 적는다.
- MMLU 는 0-shot 이다 (5-shot 은 문맥이 길어 같은 이유로 뺐다). 보통 보고하는 5-shot 점수와 직접 비교하지 않는다.
- C4 문서: `tricast.eval.ppl` 의 내장 `"c4"` 는 샤드를 datasets 스트리밍으로 읽는데, datasets 4.x 의 오프라인 모드에서는
  스트리밍 캐시를 찾지 못한다 (`Couldn't find cache for allenai/c4 for config 'en-b885fc77211cd7f4'`). 그래서 허브 캐시의
  같은 파일(`allenai/c4@1588ec45`, `en/c4-validation.00000-of-00008.json.gz`)을 직접 읽어 같은 규칙으로 잇는다. 온라인
  스트리밍으로 이은 글과 바이트 단위로 같음을 클러스터에서 확인했다 (SHA-256 `d7b24fe9…`, 2,410,955 자). 코드는 이 SHA 가
  아니면 멈춘다. `ppl.py` 는 고치지 않았다 (`tests/test_eval.py` 가 로더 인자를 고정한다).

### 1.2 셋업과 짝

- 셋업 = 화면이 내주는 레시피 파일 그대로 (`tune_bench.py recipes`: 번들의 격자를 화면과 같은 코드로 파일로 만들고, 번들이
  PPL 을 잰 파일의 SHA-256 과 다르면 멈춤 — 0.6B 21개 · 8B 7개 모두 일치).
- 모델 준비는 답변 기록(`tune_outputs.py`)과 같은 함수(`prepare`: 새 모델 → 레시피 패치 → 보정, 보정 캐시)다.
- **우리 방법** = 크기마다 Auto-tune 배정(기본 설정, AI 세부 설정 없음).
- **기존 방법** = 벤치마크마다, 그 크기(Auto-tune 에 준 예산) 안에서 잰 "모든 층에 한 방법" 가운데 **그 벤치마크 점수가 가장
  좋은 것**. 결과를 보고 고르는 것이라 기존 방법 쪽에 유리하다.
- 정확도 평균 행은 한 셋업끼리 비교한다: 기존 방법 = 정확도 평균이 가장 높은 한 방법.

### 1.3 판정

- 정확도: 같은 문항끼리 짝지은 차이(우리 − 기존)의 평균과 표준오차(차이의 표본 표준편차 / √n). |차이| > 2 SE 일 때만
  "우리 우세" / "기존 우세", 아니면 "차이 없음". 과제마다 따로 판정하고 다중 비교 보정은 하지 않는다 (과제 7개면 우연히
  하나쯤 우세가 나올 수 있다).
- 정확도 평균: 과제별 짝 차이의 평균, SE = √(Σ SE²) / 과제 수 (과제끼리 문항이 겹치지 않음).
- PPL: 문항별 기록이 없어 판정하지 않고 상대 차이(%)만 적는다.
- 과제 하나의 표준오차(짝 없음, 참고용)는 문항별 0/1 에서 lm-eval `mean_stderr` 와 같은 식(표본 표준편차 / √n)으로 낸다.
  lm-eval 자체의 표준오차는 껐다 (`bootstrap_iters=0`): LAMBADA 의 perplexity 지표가 bootstrap 을 쓰는데, 그 bootstrap 은
  CPU 수만큼 프로세스를 fork 한다 (`mp.Pool(cpu_count())`). 모델을 든 프로세스에서 strict-overcommit 호스트(berlin)와
  malmo 모두 `OSError: [Errno 12] Cannot allocate memory` 로 실패했다 (탐색 3회차). 공유 노드의 코어를 다 잡는 것도 피한다.
  `tricast.eval.lmeval.evaluate` 에 `bootstrap_iters` 인자를 더했다 (주지 않으면 이전과 같은 호출).
- 같은 문항인지: 내보내기(`tune_bench.py export`)가 셋업마다 원본(BF16) 기록과 과제별 문항 수 · 전체 수 · 상한 · 예제 수 ·
  과제 버전 · 데이터 지문 · lm-eval 버전 · 배치 설정을 대조하고, 다르면 멈춘다. 문항별 0/1 기록의 평균이 lm-eval 이 낸 점수와
  1e-9 안에서 같지 않으면 기록 단계에서 멈춘다 (발화 확인).
