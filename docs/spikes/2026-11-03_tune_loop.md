# 스파이크: 사람 없이 도는 튜닝 루프 (근거 분석 → Claude 제안 → 검사 → GPU 측정 → 수집)

## 1. 가장 위험한 가정

**"층별 근거 분석만 받은 Claude(새 문맥, 도구 없음)가 라운드마다 검사를 통과하는 제안을 내고, 사람 개입 없이 루프가 끝까지 돌며,
시작점보다 나은 배정을 찾는다."**

- 맞으면: "AI 가 모델을 자동으로 최적화한다"를 사람 없이 재현할 수 있다.
- 틀리면 둘 중 하나다.
  - 제안이 검사(예산 · 근거 · 숫자)를 못 넘는다: 분석 형식이나 규칙 전달이 부족하다.
  - 측정에서 나아지지 않는다: 이 세션 바깥의 지식 없이는 개선을 찾지 못한다.
- 지휘 세션이 손으로 도는 루프([2026-11-03_tune_agent.md](./2026-11-03_tune_agent.md))와 다른 점은 다음과 같다.
  - 제안자가 라운드마다 새로 시작한다.
  - 제안자가 보는 것은 분석 JSON 뿐이다.
  - 제안 이후의 모든 단계가 코드로 돈다.

## 2. 시간 제한

2 라운드 × 제안 4개. 측정은 라운드당 약 20분(A100 1장). 제안 호출은 라운드당 비용 상한 2달러(`--max-budget-usd`).

## 3. 성공 조건 (실행 전에 확정)

**공통 설정**
- 모델 Qwen3-0.6B, 표는 Auto-tune v2 표 (validation 창, seed 42), 크기 예산 **285/56 비트**.
- 시작점: v2 의 `auto_5.09` 배정. 같은 레시피 해시이고, 검증 KL 은 v2 측정값(validation seed 43)을 그대로 쓴다.
- 세션 프로토콜은 `app/tune_agent.MEASURE_DEFAULTS`, 제안 엔진은 `claude-code` (기본 모델).

| # | 조건 | 판정 |
|:-:|---|---|
| L1 | 2 라운드가 사람 개입 없이 끝난다 | `loop/summary.json` 에 라운드 2개가 있다. 각 라운드는 다음을 만족한다. ① 제안자 호출 기록 `llm/round_<n>.json` 이 있다. ② 통과 제안이 1개 이상이다. ③ 측정 결과가 ledger 에 들어갔다. |
| L2 | 루프가 찾은 최선의 검증 KL < 시작점 `auto_5.09` 의 검증 KL | GPU 측정 |
| L3 | 통과율: 제안자가 낸 제안 중 검사를 통과한 비율 ≥ 50% | 기록 |

- **채택**: L1 · L2 통과. L3 는 보고만 한다.
- 실행 도중 사람이 개입하면(제안 수정 · 재시작 · 측정 재시도) L1 은 실패로 적는다. 인프라 장애로 다시 시작한 경우에는 그 사실과 이유를 적는다.
- test PPL 은 루프 안에서 재지 않는다. 최선의 레시피는 루프가 끝난 뒤 1회만 잰다 (보조, 판정에 쓰지 않음).

## 4. 방법

1. 세션 `runs/20261103_tune/loop_s2` 를 만들고 `auto_5.09` 를 시작 제안으로 등록한다 (레시피 해시 확인).
2. `python -m app.tune_loop run --config <loop.json> --rounds 2 --per-round 4 --proposer claude-code` 를 지휘 세션이 한 번 실행한다. 그 뒤로는 손대지 않는다.
3. 측정은 geneva A100 에서 `gpu_cap.sh` 를 거친다. 트리는 수정 없는 커밋 클론이다.
