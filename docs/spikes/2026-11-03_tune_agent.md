# 스파이크: 측정 기록을 검색(RAG)하는 에이전트가 같은 측정 예산의 자동 탐색보다 나은 층별 배정을 찾는가

## 1. 가장 위험한 가정

**"층 × 방법 표와 지금까지의 측정 기록(ledger)을 근거로 후보를 고르는 LLM 에이전트는, 표 예측 순위만 따르는 자동 탐색과 같은 측정
횟수로 더 나은 배정을 찾는다."**

- 맞으면: "AI 가 최적 옵션을 찾는다"는 기능에 에이전트가 필요하다.
- 틀리면: 같은 예산의 자동 탐색으로 충분하다. 에이전트는 설명 도구일 뿐 탐색 도구가 아니다.
- 근거:
  - v1 의 예측 합은 실측의 1.4~2.1배였고, 순서는 맞았다 (ρ 0.97).
  - 층 끝 블록 보호처럼 표에 없는 상호작용이 PPL 을 바꾼 사례가 있다 (W1: 0/27 블록 BF16).
  - 방법 옵션(스케일 방법 · 반올림 · 그룹)은 표에 없다. 그래서 자동 탐색은 옵션을 바꿀 수 없지만, 에이전트는 측정으로 시험할 수 있다.

## 2. 시간 제한

arm 마다 4 라운드 × 측정 4회 (KL 16회). 레시피당 검증 KL 은 약 20초, 보정 레시피는 보정 시간이 더해진다. 그 뒤 arm 마다 PPL 1회.
A100 1장, 1일.

## 3. 성공 조건 (루프 전에 확정)

**공통 설정**
- 표: Auto-tune v2 표 ([2026-11-03_autotune_v2.md](./2026-11-03_autotune_v2.md)), 크기 예산 **4.50 비트**.
- 출발점: A0 = v2 의 `solve --budget-bits 9/2` 배정.
- 검증 지표: 레시피 전체 KL. WikiText-2 **validation**, seed 43, 8 × 512 창 (`app.tune_agent` 세션 프로토콜). 보정은 train 에서 뽑으므로 보정 창과 겹치지 않는다. 표의 validation seed 42 창과의 겹침은 v2 스파이크 C2 의 `--overlap` 으로 기록한다.
- 최종 지표: WikiText-2 test PPL (146 × 2048 창). arm 마다 끝에 1회만 잰다.

**arm**
- **A0**: 출발점 그대로 (탐색 없음).
- **A1 (에이전트)**:
  - 라운드마다 제안을 최대 4개 낸다. 4.50 비트 안의 어떤 격자든 되고, 방법 옵션 · 보정 설정도 바꿀 수 있다.
  - 근거 규칙은 `docs/prompts/tune_agent.md` 를 따른다.
  - 라운드가 끝날 때마다 검증 KL 이 가장 낮은 것을 현재 최선으로 둔다.
- **A2 (자동 대조군)**:
  - 라운드마다 현재 최선에서 `app.tune_agent neighbors` 의 예측 변화가 작은 순서로 아직 재지 않은 이웃 4개를 잰다. 이 순위는 표에 바닥 차감을 적용해 매긴다.
  - 검증 KL 이 현재 최선보다 낮으면 그 이웃으로 옮긴다.
  - 사람 · LLM 판단은 없다.

| # | 조건 | 판정 |
|:-:|---|---|
| S1 | A1 최종 선택의 검증 KL < A0 의 검증 KL | GPU 측정 |
| S2 | A1 최종 선택의 test PPL < A0 의 test PPL | GPU 측정 |
| S3 | A1 최종 선택의 test PPL ≤ A2 최종 선택의 test PPL | GPU 측정 |

- **채택**: S1 · S2 · S3 모두 통과.
- **해석**:
  - S1 만 통과: 8개 창에 맞춘 것이 test 로 이어지지 않았다 (검증 과적합).
  - S2 는 통과, S3 실패: 개선은 측정 피드백 덕분이지 LLM 판단 덕분이 아니다.
- 측정 예산: arm 마다 KL 16회 이하, PPL 1회. 남은 예산을 다 쓰지 않아도 된다. A1 은 예산을 남기고 멈춰도 된다.
- 동률 규칙: 검증 KL 이 같으면 평균 비트가 작은 쪽, 그다음 이름 순.
- 공개 범위: A1 의 모든 제안을 보고한다. 측정하지 못한 것, 거부된 것, 이유, 인용 id, 측정 파일 해시를 포함한다.

## 4. 방법

1. 측정 기록 수집: `python -m app.ledger ingest runs/… --ledger runs/ledger.jsonl` 을 실행하고 `verify` 가 불일치 0 이어야 한다.
2. A0: v2 스파이크에서 이미 잰 `auto_4.50` 의 검증 KL 과 PPL 을 그대로 쓴다. 같은 레시피 해시인지 확인한다.
3. A1 · A2 는 같은 라운드에 함께 잰다 (측정 작업 하나에 최대 8개 레시피). 라운드 r 의 A2 이웃은 라운드 r−1 까지의 A2 결과만 보고 정한다.
4. 4 라운드 뒤, 각 arm 의 최종 선택을 `tricast run` 으로 PPL 1회 잰다. 같은 GPU 종류(A100)에서 잰다.
5. 에이전트는 검증 KL 결과만 보고 다음 라운드를 정한다. test PPL 은 4번 이전에 어떤 후보에 대해서도 재지 않는다.

해석 주의 (결과와 무관하게 보고에 적는다):
- 에이전트는 v1 결과와 이 저장소의 문서를 이미 읽은 상태다. 그래서 이 스파이크는 "빈 상태의 LLM"이 아니라 "이 기록을 가진 에이전트"를 잰다.
- 검증 KL 은 8개 창(4,096 토큰)이다.
- 방법 옵션은 A1 만 바꿀 수 있다. 차이가 옵션에서 나왔는지는 A1 제안 기록으로 따로 적는다.
