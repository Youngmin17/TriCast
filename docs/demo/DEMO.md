# TriCast: 3분 발표 시나리오

**한 문장:** “같은 모델에서 수 형식과 누산 산술을 따로 바꾸고, 그 선택이
모델 품질에 미치는 영향을 한 장의 GPU로 비교합니다.”

실행법은 [examples/README.md](../../examples/README.md), 수치 의미론의 기준은
[ENGINE.md](../design/ENGINE.md)입니다. 아래 3분은 **발표 시간**입니다.
전체 평가가 3분에 끝난다는 실측 주장이 아닙니다.

## 사전 준비

1. GPU 운영자가 한 슬롯을 배정한 뒤 다음 명령을 실행합니다.
   모델·WikiText-2 다운로드와 Triton 첫 컴파일은 발표 전에 끝냅니다.

   ```bash
   PYTHONNOUSERSITE=1 CUBLAS_WORKSPACE_CONFIG=:4096:8 \
     /scratch/uceeeee/conda_envs/tricast/bin/python examples/demo_qwen3.py \
     --quick --skip-gptq
   ```

2. `DEMO_DONE` 마커, `results.json`의 전체·행별 상태와 `report.md`를 확인합니다.
   실패한 행을 성공 사례로 읽지 않습니다. 시간 예산이 부족하면
   `--max-windows 2`로 리허설하되, 발표 표에 실제 윈도우 수를 밝힙니다.
3. `env.json`에서 소스 SHA/dirty 여부, 모델 commit, GPU, 패키지 버전, seed와
   데이터셋 fingerprint를 확인합니다. 원본 가중치 복원 검증과 패치된 모듈의
   forward 호출 기록도 확인합니다. 이 기록은 **커널 bit-exact 검증을 대체하지 않습니다**.
4. GPTQ·정적 EMA는 별도 보정이 필요한데 Lane D 허용 API에 `calibrate`가 없습니다.
   현재는 명시적으로 실패를 기록합니다. 발표 명령은 `--skip-gptq`를 사용합니다.
   RTN 결과를 GPTQ라고 부르지 않습니다.

## 0:00–0:25 — 문제와 입력

**화면:** 실행 명령, 모델 이름, `report.md`의 환경 요약.

**말할 내용:** “FP8이라는 이름만으로 덧셈 과정은 정해지지 않습니다.
TriCast는 원소 형식, 스케일, 누산 알고리즘을 분리합니다. 오늘은 같은 Qwen3
가중치에서 이 세 가지 선택을 비교합니다.”

**범위:** 기본 모델은 `Qwen/Qwen3-0.6B`, BF16 로드, seed 42.
하드웨어 프리셋 이름은 **에뮬레이션할 산술**을 뜻하며, 해당 GPU에서 네이티브
텐서코어를 실행했다거나 실리콘과의 일치가 검증됐다는 뜻이 아닙니다.

## 0:25–1:00 — 형식 한눈에

**화면:** `formats` 표. 같은 `q_proj` 가중치를 BF16, FP8, MXFP8/6/4,
NVFP4/4o6, MSFP12, INT4로 바꾼 결과입니다.

**메시지:** “원소당 비트를 줄일 때 어떤 오차를 지불하는지 보입니다.
스케일도 저장해야 하므로 FP4라는 이름이 총 4비트 비용을 뜻하지는 않습니다.”

- SQNR(dB)는 `10 log10(Σw² / Σ(w−ŵ)²)`: 높을수록 이 가중치의 복원 오차가 작습니다.
  오차가 정확히 0이면 `inf`이며 누락값이 아닙니다.
- 최대 절대 오차는 가장 크게 달라진 한 원소의 크기입니다. 평균 품질 지표가 아닙니다.
- 비트/원소는 **논리적 형식 payload**입니다. 원소 수 × 형식 비트 + 실제 스케일 개수 ×
  스케일 비트 + global scale 32비트 + zero-point 비트를 원소 수로 나눕니다.
  마지막 짧은 그룹도 스케일 하나를 셉니다.
- 정수 zero point는 원소 형식 폭, 실수 zero point는 FP32라는 저장 가정을 씁니다.
  `UE4M3`는 현재 계약의 unsigned 7비트를 사용합니다. 실제 NVFP4의 8비트 스케일
  컨테이너나 PyTorch의 FP32 저장 메모리, padding, 패킹 효율을 주장하는 표가 아닙니다.
  `msfp12`도 이름의 숫자가 아니라 계약의 원소/공유 지수 비트로 계산합니다.

**실측:** SQNR·최대 오차·비트/원소 표 — **실측 후 채움**.
형식마다 품질 순서가 반드시 정해져 있다고 말하지 않습니다.

## 1:00–1:40 — 같은 FP8, 다른 누산

**화면:** `accumulation` 표에서 FP64 기준, Blackwell/Hopper/Ada 프리셋,
Hopper 기반 `F=7 fused`와 `F=7 decoupled` 행을 비교합니다.

**메시지:** “입력과 가중치의 양자화 값은 고정했습니다. 이제 바뀌는 것은
누산 산술입니다. F=7에서 부분합을 계속 같은 정밀도로 합칠지, F2=23의
분리된 누산기에 모을지 선택할 수 있습니다.”

- 짧은 프롬프트로 11번째 `mlp.down_proj`의 입력을 hook으로 받습니다.
  작은 모델에서는 마지막 레이어를 사용합니다.
- 앞 4개 입력 행 × 앞 32개 출력 채널만 사용하지만 K 축은 자르지 않습니다.
  두 부분행렬 자체를 FP8 per-tensor로 한 번 양자화해 모든 프리셋에 재사용합니다.
  **전체 레이어 출력 또는 전체 모델의 오차가 아닙니다.**
- 상대 Frobenius 오차는 `‖Y−Yref‖F / ‖Yref‖F`. 기준은 같은 양자화 피연산자의
  FP64 누산 후 FP32 출력입니다. 원래 비양자화 가중치와의 오차가 아닙니다.
- BF16 비트 불일치 비율은 두 FP32 출력을 BF16으로 변환한 뒤 16비트 패턴을
  비교한 원소 비율입니다. 0이면 이 표본에서만 같다는 뜻입니다.
- 시간은 CUDA-core 에뮬레이션 경과 시간입니다. warmup 3회, 측정 5회;
  p99는 5개 표본의 선형 보간값일 뿐 안정적인 tail-latency 추정이 아닙니다.

**실측:** 상대 오차·불일치 비율·시간 — **실측 후 채움**.
누산 순위나 `decoupled`의 우위를 결과 전에 단정하지 않습니다.

## 1:40–2:15 — 모델 품질로 연결

**화면:** `quality` 표의 PPL, 레시피, 경과 시간과 실제 윈도우 수.

**메시지:** “작은 행렬의 오차만으로 모델 품질을 단정하지 않고,
같은 WikiText-2 토큰에서 레시피별 PPL을 비교합니다.”

- PPL은 낮을수록 이 데이터의 다음 토큰을 더 잘 예측합니다. 모델·토크나이저·
  데이터 fingerprint·윈도우 수가 같은 행만 비교합니다.
- quick은 앞 16개 완전한 2048-token 윈도우까지입니다. 윈도우의 첫 토큰과
  마지막 불완전 윈도우는 채점하지 않습니다. 전체 test PPL로 부르지 않습니다.
- `bf16_passthrough`는 레시피가 정의한 누산 기준입니다. 네이티브 HF GEMM과
  bit-exact하다고 가정하지 않습니다. 생성 표의 `native`는 패치하지 않은 모델입니다.
- 레시피마다 unpatch → patch → 실행 → unpatch를 수행하고, 모든 원본 Linear의
  weight/bias 해시와 모듈 동일성을 확인합니다. 검증 실패는 해당 행을 실패로 표시합니다.
- 경과 시간은 패치·평가·복원 검증까지 포함한 **1회 관측치**로, 속도 우열의 근거가 아닙니다.

**실측:** PPL·실제 윈도우/토큰 수·경과 시간 — **실측 후 채움**.

## 2:15–2:45 — 생성 비교

**화면:** `generation` 표. 한국어·영어 프롬프트 각각에 대해 native BF16,
Hopper FP8, FP8 F=7 fused, MXFP4 결과를 옆으로 보여줍니다.

**메시지:** “숫자 차이가 실제 출력 문장에도 나타나는지 직접 확인합니다.
다만 두 문장은 벤치마크를 대체하지 않습니다.”

같은 chat template, `enable_thinking=False`, greedy(`do_sample=False`, beam 1),
최대 48개 신규 토큰을 사용합니다. EOS로 일찍 끝나거나, 제한에 의해 문장이
잘리거나, 모든 설정이 같은 답을 내놓을 수 있습니다. 차이를 억지로 만들지 않습니다.
`--dtype`를 바꿨다면 `native`의 실제 dtype도 함께 밝힙니다.

**실측:** 프롬프트별 네 가지 생성 문장 — **실측 후 채움**.

## 2:45–3:00 — 결론과 산출물

**화면:** `results.json`, `report.md`, `env.json`.

**마무리:** “TriCast의 가치는 특정 비트 수가 항상 좋다는 결론이 아니라,
새 수 형식과 누산 설계를 같은 모델에서 재현 가능한 방식으로 비교하는 데 있습니다.”

커널 bit-exact 검증, 실제 Qwen3 GPU 완주, 수 분 실행 목표, GPTQ 보정 연결은
각각 별도 검증 항목입니다. 아직 결과가 없는 칸은 **실측 후 채움**으로 남깁니다.
