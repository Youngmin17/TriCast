# 논문 실험 프로토콜 — 근거를 읽는 에이전트가 층마다 양자화 방법을 섞는다

## 1. 주장 (감사 후)

감사 결론 (survey.yaml `verdict`):
- 단일 층 KL 표 + 가산 + 정확 할당(우리 v2 의 뼈대)은 선점됐다. ZeroQ 2020, HIGGS, ModelOpt `kl_div`, Hill 2026 이 있다. 그래서 **기여가 아니라 강한 기준선**으로 둔다.
- "방법 혼합 > 비트 혼합"은 CALM Tab 4 가 이미 보였다. 그래서 주장에서 내리고 확인 실험(절제)으로만 둔다.
- 선점을 찾지 못한 것은 아래 H2 다. 가장 큰 위험은 본문을 확인하지 못한 동시기 ICLR'27 제출물 두 편(AutoQS, Explorer–Reviewer)이다.

| # | 주장 | 반증 조건 |
|:-:|---|---|
| **H2 (주)** | 측정 원장을 인용하고 결정적 검사(예산 · 레코드 id 실존 · 수치 지지)를 통과해야 하는 LLM 에이전트가 Linear 단위 이질 공간에서, 같은 전체 모델 측정 수로 강한 기준선보다 낮은 검증 KL 을 찾는다. 강한 기준선은 Hill 식 가산 배낭 · ModelOpt AutoQuantize · EvoPress · AMQ · TPE · LLM-seeded BO 다. held-out test 에서도 같은 방향이다 | any-time 곡선의 예산점 다수에서 에이전트가 최선 기준선보다 낫지 않다 |
| H2a (기제) | 이득은 근거 인용과 검사에서 온다. 무원장 · 무검사 · 무이력 LLM 은 이득이 줄거나 사라진다 | 절제 arm 이 전체 에이전트와 같다 |
| H3 (부) | 다른 모델의 원장을 가진 에이전트가 새 모델에서 같은 KL 에 더 적은 측정으로 닿는다 | 원장 없는 에이전트와 곡선이 같다 |
| H4 (부) | 비트 예산이 낮을수록 가산 예측의 오차(비가산성)가 커지고, 그만큼 측정 피드백(에이전트 · 블랙박스)의 이득이 커진다 | 예측-실측 순위 상관과 이득이 예산과 무관하다 |

지금까지의 근거 (Qwen3-0.6B 한 모델, 사전 등록 스파이크):
- 4.50 비트 표 + 배낭은 test PPL 21.88 이다.
- 지휘 세션 에이전트 21.635, 자동 탐욕 21.859 였다. 자율 루프는 285/56 비트에서 검증 KL 을 −7.2% 줄였다.
- 한계: 측정 8–16회, 시드 1개, 기준선은 탐욕 하나뿐이었다. 이득은 주로 GPTQ 옵션(act_order · damp · mse)이었다. 그래서 "옵션 전역 sweep" 기준선이 필요하다 (§6).

## 2. 탐색 공간

- 칸: decoder 블록 × Linear 종류 7 (`q/k/v/o/gate/up/down`). 칸마다 방법 1개를 고른다.
- 방법 옵션: 방법마다 전역으로 둔다 (`app/quantizer_recipe.OPTIONS`, `when` 조건 포함). 예: GPTQ 의 `act_order` · `damp` · group, 스케일 방법.
- KV: 블록별 preset (`--kv-presets`). 트랙 C 에서만 연다.
- 가지치기(`prune:`): 1차 실험에서는 닫는다. 공식 GPTQ 와 함께 쓰면 0 이 다시 채워진다 (사용자 결정 대기).

## 3. 두 트랙 — 비용을 공정하게 센다

지금 예산은 Linear 가중치 저장 비트만 센다. 그래서 W4A16(GPTQ)과 W4A4(NVFP4)가 같은 4.x 비트로 취급되고, 활성값 양자화의 연산 이득은 비용에 안 들어간다. 섞인 표에서 배낭이 W4A16 을 고르는 것(4.50 비트 배정의 148/196 칸)은 이 회계 탓일 수 있다. 그래서 트랙을 나눈다.

| 트랙 | 방법 풀 | 제약 | 비교 대상 문헌 |
|---|---|---|---|
| **M (메모리)** | 가중치 전용(A16): GPTQ int2/3/4 · AWQ(W-only) · HQQ 2/3/4 · NF4 · RTN, + INT8 | 평균 가중치 저장 비트 ≤ B | 혼합 정밀도 PTQ (SliM-LLM 등, 감사로 확정) |
| **C (칩 연산)** | 칩 형식 W×A: NVFP4 · MXFP4 · MXFP8 · INT8 · SmoothQuant · AWQ+NVFP4 · RaZeR · Four-over-Six (+ 회전 계열은 흡수 후) | 가중치 비트 ≤ B **그리고** 연산 비용 ≤ C | W4A4/FP4 PTQ |

- 트랙 C 의 연산 비용은 MAC 가중 합으로 센다. 가중치는 형식별 텐서코어 처리량의 역수다.
  - 후보는 FP4 : FP8 : FP16 = 4 : 2 : 1 (B200 dense) 이다. **미검증**: 데이터시트 출처를 확인하기 전에는 쓰지 않는다.
  - 출처는 HardwarePreset 의 provenance 규칙을 따른다.
- 트랙 C 에서 TriCast 의 칩 수치(누산 규칙)를 비트 단위로 같게 에뮬레이트하는 것이 차별점이다. 평가는 `mma_input` 을 명시한다.
- 풀 확장 (`dd36b02`, LOWBIT): 트랙 M 은 gptq_int3 · gptq_int2 · hqq_int3 · hqq_int2 · awq_int4, 트랙 C 는 had_nvfp4 · had_mxfp4 다.
  - hqq_int3 은 저장 비트를 3.5 로 적게 센다 (실제 약 3.7: int32 하나에 3비트 코드 10개). 비트가 고쳐질 때까지 실험 풀에서 뺀다.
  - 예산의 비트는 배포 형식의 명목 저장 비트다. 텐서당 fp32 스케일(had_*)은 빼고, AWQ 채널 스케일은 접어 넣는다고 가정한다. 이 정의를 논문에 적는다.
  - 트랙 M 에는 8비트 가중치 전용 방법이 아직 없다 (int8 은 W8A8). 4.25 비트 이상 예산에서 올릴 선택지가 bf16 뿐이라 추가가 필요하다.

## 4. 목적 · 측정 · 예산 회계

- 탐색 목적: 전체 레시피 검증 KL. WikiText-2 validation 8 × 512 창, seed 43 (`app/tune_agent.MEASURE_DEFAULTS`). 보정 창은 train 이고 겹침 0 을 기록한다.
- **측정 1회** = 레시피 1개의 검증 KL 1회. 비교군마다 같은 N 을 준다 (`--stale-rounds 0`, 라운드 × 라운드당 제안).
- 공통 비용은 모든 방법이 공유하고 따로 보고한다: 층별 KL 표(배낭 · 탐욕 · 에이전트 분석이 쓴다)와 보정 Hessian/결과 캐시.
- 블랙박스 방법은 표를 쓰지 않는 변형도 보고한다. 표 비용을 측정 수로 환산해 "표 없이 같은 GPU 시간" 비교를 한다.
- 비용 보고: GPU 시간(측정 · 표 · 보정 분리), LLM 비용($ · 입력/출력 토큰), 벽시계.
- **한 칸의 모든 측정은 같은 GPU 모델 · 같은 트리에서 한다.** 같은 GPU · 같은 트리에서는 측정이 float 로 결정적이다. 그러나 A100 과 H200 사이에서는 같은 레시피의 KL 이 최대 5.5% 다르고, 가까운 제안의 순위가 바뀐다 (증거 문서, 보정 캐시 게이트 · 귀속). 그래서 다음을 지킨다.
  - 칸마다 GPU 모델을 하나로 고정한다. 코드가 강제한다: 세션이 loop.json 의 `gpu` 를 고정하고(`tune_agent.pin_gpu`), 다른 GPU 의 측정은 이력에 넣지 않으며 `kl.json` 도 거부한다.
  - 최종 평가도 같은 GPU 에서 한다.
  - 다른 GPU 에서 최선 레시피들을 다시 재어 순위 상관을 보고한다.
- 최종 평가는 탐색이 끝난 뒤 최선 레시피 하나만 1회 잰다. 선택에는 쓰지 않는다.
  - WikiText-2 test PPL (2048 창), C4 validation PPL (GPTQ 프로토콜)
  - lm-eval zero-shot: ARC-e/c · HellaSwag · PIQA · WinoGrande · LAMBADA · BoolQ. 과제별 점수와 표본 수를 보고한다.
  - MMLU 5-shot

## 7. 반복 · 통계 · 보고

- 예산: 단일 N 이 아니라 **any-time 곡선**을 그린다. 측정 N ∈ {8, 16, 32, 64} (+ 128 은 0.6B 만). 우열 역전을 숨기지 않는다. 근거: zhang-arxiv23 Tab 5, RE-Bench.
- 반복: 블랙박스는 seed 0–4. 에이전트는 독립 실행 ≥3. (모델, 트랙, 예산) 칸마다 반복한다. 에이전트 실행 간 성공률도 보고한다.
- 검정: 칸 단위 짝 비교. 정확 sign-flip 순열 검정을 쓰고, 주장 여럿은 Holm 으로 보정한다 (quant-eval 의 작은 n 규칙).
- 선택 편향: 탐색은 검증 KL 로 하고 보고는 held-out 으로 한다. 방법별로 본 후보 수, 검증–test 순위 상관, top-k 의 test 분포를 함께 낸다. 근거: AIRA-dojo §5.3.
- 무효 제안 회계: 거부된 제안은 측정 예산에 넣지 않는다 (`--measurements` 가 보충한다). 거부율 · 거부 사유 · 예산 미달(shortfall)을 보고한다.
- 수치 충실도 감사: 보고서와 로그의 모든 수치가 원장 레코드 id 로 역추적되는지 자동 검사하고 통과율을 낸다 (`app.ledger verify`).
- 비용 표: 방법별로 LLM 입력/출력 토큰 · $ · 벽시계 · GPU 시간(측정 · 표 · 보정 분리)을 한 표로 낸다.
- 하드웨어 강건성: 칸마다 각 arm 의 상위 k 레시피를 두 번째 GPU 모델에서 다시 재어 Spearman 순위 상관과 "최선이 최선으로 남는가"를 보고한다.
- 잡음 바닥: 같은 레시피의 KL 이 GPU 간에 1–5% 움직인다 (사후 진단, Qwen3-0.6B, A100 vs H200, Spearman 0.61). 그래서 다음 둘을 함께 낸다.
  - 칸마다 잡음 바닥: 보정 seed 와 GPU 를 바꾼 반복 측정의 분산
  - 그 바닥을 넘는 이득만 "개선"으로 세는 판정
  - 에이전트가 바닥 아래의 차이에 맞춰 고르는 과적합도 절제(같은 N, 두 GPU 평균 KL 로 선택)로 잰다.
